# ТЗ для разработки: Android-приложение оцифровки керна («Долбление / Стол»)

Документ для разработчика (Android Studio) и для Claude Code. Это
**инженерное ТЗ**: домен, архитектура, экраны, требования к камере, схема
локального хранилища, точный контракт интеграции с сервером **s900** (проект
`s8`, этот репозиторий) и пошаговый план реализации.

Исходное бизнес-ТЗ: `TZ_Android_kern.docx` (в корне репозитория). Этот файл —
его инженерная детализация; при расхождениях бизнес-ТЗ приоритетнее в части
*что* делать, этот файл приоритетнее в части *как*.

> ⚠️ Приложение — **отдельный проект** (Android Studio / Kotlin), а не модуль
> реактора `s8`. Этот файл лежит в репозитории `s8` только как источник знаний
> об интеграции. При старте Android-проекта скопируйте разделы 3, 8 и 12 в его
> `CLAUDE.md`.

## 1. Назначение и суть

Мобильное приложение для Android — специализированный инструмент оцифровки
геологических образцов (колонок керна). Оператор в фотокабине снимает лотки
керна **парами кадров** (дневной свет + УФ), приложение хранит их локально и
пакетно отправляет на сервер s900 для анализа в виде **наложенных слоёв
(стека)**.

**Критическое требование проекта** (проходит через весь дизайн): гарантия
**абсолютной идентичности условий съёмки** за счёт фиксированных, сохраняемых
профилей камеры с полностью отключённой автоматикой (AE/AWB/AF). Одна и та же
порода должна выглядеть одинаково на всех кадрах одной фотокабины — от снимка к
снимку и от сессии к сессии.

## 2. Глоссарий и доменная модель

| Термин в приложении | Смысл | Сущность на сервере s900 |
|---|---|---|
| **Долбление** (Drilling) | Набор колонок керна за один этап бурения. Верхний контейнер съёмки; несёт паспортные данные. | `AnalysisSource` (проект) |
| **Стол** (Table) | Конкретный лоток/короб с керном. Внутри долбления нумеруется №1, №2, … | `FieldOfView` (тип `STACK`) |
| **Слой** (Layer/Shot) | Один кадр стола с типом освещения. Всегда пара: Дневной + УФ. | `SourceImage` c атрибутом `lampType` |
| **Стек** (Stack) | Логически связанная пара слоёв одного стола (наложение). | `FieldOfView` со списком `SourceImage`, группировка по `stack_uid` |
| **Профиль камеры** | Сохранённый набор ручных параметров съёмки под тип освещения. | — (только на клиенте) |
| **Паспортные поля** | Метаданные долбления, задаваемые пользователем. | атрибуты `AnalysisSource` (`@JsonAnySetter` → `attributes`) |

**Иерархия данных:**

```
Долбление (AnalysisSource)
├── паспортные поля (title + произвольные атрибуты)
├── Стол №1 (FieldOfView / stack)
│   ├── Слой DAYLIGHT (SourceImage, lampType=DAYLIGHT, stack_uid=UID1)
│   └── Слой UF       (SourceImage, lampType=UF,       stack_uid=UID1)
├── Стол №2 (FieldOfView / stack)
│   ├── Слой DAYLIGHT (stack_uid=UID2)
│   └── Слой UF       (stack_uid=UID2)
└── ...
```

**Тип освещения** на сервере — enum `LampType`: **`DAYLIGHT`** и **`UF`** (ровно
эти строки в JSON; см. `data/.../analysis/source/LampType.java` и
`s8-api/.../dto/LampTypeDto.java`). УФ = `UF` (не «UV»).

**Назначение данных в s900 (подтверждено по коду).** Залитое долбление попадает
в модуль **«Фотокнига керна» / каротаж (Core Photo Book, `/s8/core/photo/book`)**
— туда же, куда ложатся данные сканера GEO 360. Керны (`Core`) для фотокниги
**строятся на стороне сервера** post-upload-обработкой из `FieldOfView`, а не
создаются приложением (`POST /core` — заглушка). Приложение отвечает только за
корректный `AnalysisSource` + изображения с правильными атрибутами.

Ключевое соответствие терминов (подтверждено локализацией `ui_ru.xml` и
`AttrUtil`): app-термин **«Долбление» = атрибут `perforation_number` = «Номер
долбления»** в фотокниге керна. Паспортные поля — это не «произвольная схема», а
**конкретный набор гео-атрибутов** `AnalysisSource` (см. §8.5).

## 3. Технологический стек (рекомендация)

| Слой | Технология | Обоснование |
|---|---|---|
| Язык | **Kotlin** | стандарт Android |
| Min SDK | **API 26 (Android 8.0)** | нужен полноценный Camera2 manual capture |
| Target SDK | последний стабильный | требования Play/безопасность |
| Камера | **Camera2 API** (не CameraX для captureRequest) | нужен полный ручной контроль и блокировка AE/AWB/AF — см. §6 |
| UI | **Jetpack Compose** (или View + ViewBinding) | современный, быстрый |
| Локальная БД | **Room** | долбления/столы/слои/статусы (§7) |
| Файлы фото | внутреннее хранилище приложения (`filesDir`) | защита данных до отправки |
| Настройки/профили | **Jetpack DataStore (Proto/Preferences)** | глобальные профили камеры и настройки сервера |
| Сеть | **Retrofit + OkHttp** (multipart, Basic auth, таймауты, ретраи) | REST-интеграция с s900 |
| Очередь отправки | **WorkManager** | надёжная фоновая отправка с ретраями (§9) |
| Асинхронность | **Coroutines + Flow** | — |
| DI | **Hilt** | — |

**Разрешения:** `CAMERA`; хранение — внутреннее (разрешения на storage не нужны);
`INTERNET`, `ACCESS_NETWORK_STATE`. Работа по TCP/IP на любой сети (Wi-Fi,
мобильные данные, Ethernet, VPN).

## 4. Архитектура приложения

Слоистая архитектура (Clean-ish), однонаправленный поток данных:

```
UI (Compose screens) ── ViewModel (StateFlow) ── UseCase/Repository
                                                   ├── Room DAO (локальный источник истины)
                                                   ├── FileStorage (фото во filesDir)
                                                   ├── CameraController (Camera2 + профили)
                                                   └── S900Api (Retrofit) — только при синхронизации
```

Принципы:
- **Локальный источник истины** — Room + файлы. Сеть эпизодическая (§2 бизнес-ТЗ):
  тест соединения, загрузка конфигурации полей, экспорт.
- **Автосохранение** — любое изменение пишется в Room немедленно; отдельной
  кнопки «Сохранить» нет.
- **Оффлайн-first** — приложение полностью работоспособно без сервера.

## 5. Экраны и навигация

> Визуальный стиль всех экранов — **§14 «Дизайн-система»** (палитра/типографика/
> компоненты navy-темы s900). Экраны съёмки/просмотра — тёмные (§14.7),
> остальные — светлые.

Навигация (граф):

```
[Настройки/Первый запуск] ──▶ [Список долблений] ─┬─▶ [Форма долбления] ──▶ [Съёмка]
                                                   ├─▶ [Столы долбления] ──▶ [Просмотр стола] ──▶ [Съёмка (досъёмка)]
                                                   ├─▶ [Профили камеры]
                                                   └─▶ [Отправка / очередь]
```

### 5.1. Первый запуск / Настройки сервера
- Поля: **IP/домен** (обяз.), **порт** (обяз., default `8080`), **протокол
  HTTP/HTTPS** (опц.), **логин** и **пароль** s900.
- Кнопки: «Сохранить настройки», «**Проверить соединение**» (тест + авторизация,
  показать успех/ошибку).
- После успеха — попытка загрузить **конфигурацию паспортных полей** (§8.5).
  Успех → полный набор полей; неудача/недоступен → упрощённый режим (только
  название долбления).
- Отдельно: «**Загрузить конфигурацию полей**» (принудительно), дата/время
  последней загрузки, просмотр текущего списка полей.

### 5.2. Список долблений (главный экран)
- Список карточек долблений; на каждой — название и **статус отправки**
  (Не отправлено / Отправлено / Ошибка / Отправляется + прогресс).
- Кнопка «**Новое долбление**».
- Действия над элементом: открыть (→ столы), удалить целиком (с подтверждением),
  отправить.
- Мультивыбор для пакетной отправки (§5.6).

### 5.3. Форма долбления
- **С конфигурацией полей**: динамическая форма по загруженной схеме полей.
- **Без конфигурации**: одно поле «Название серии/долбления» (например,
  «Керн-456, 150–155 м»).
- При сохранении: генерируется уникальный внутренний `id` (UUID) → переход в
  режим съёмки со «Стол №1», активный профиль **«Дневной свет»**.

### 5.4. Режим съёмки (ключевой экран)
- Полноэкранный превью Camera2 с наложенным HUD:
  - индикатор «**Стол №N**», индикатор активного типа освещения
    (**Дневной / УФ**), текущие параметры профиля (выдержка/ISO/WB/фокус).
  - переключатель **Дневной ⇄ УФ** — при переключении **мгновенно** применяется
    сохранённый профиль соответствующего типа (§6).
  - кнопка спуска.
  - «**Новый стол**» / «Далее» — инкремент счётчика стола, авто-сброс профиля на
    «Дневной свет».
  - «Назад» — в список долблений; всё уже сохранено.
- Логика пары: снятые Дневной+УФ одного стола связываются в один стол (стек).
  В галерее — единый элемент с переключением слоёв.
- Метки кадра: `lampType` (DAYLIGHT/UF), номер стола, снимок привязки профиля.

### 5.5. Столы долбления / Просмотр стола
- **Столы**: сетка карточек. Превью карточки — кадр Дневного света; если есть УФ
  — бейдж/иконка переключения слоёв.
- **Просмотр стола**: пара снимков с переключением слоёв (свайп / тап по иконке /
  ползунок наложения) для сравнения.
- Действия: **Доснять/переснять** слой (камера с привязкой к столу, применяются
  профили), удалить стол или отдельный слой, редактировать номер стола и
  паспортные данные долбления. Всё — с автосохранением.

### 5.6. Отправка / очередь
- Список долблений со статусами; выбор одного/нескольких → «**Отправить на
  сервер**».
- Прогресс отправки и итоговый статус по каждому долблению.
- Повтор отправки для неудачных; очистка успешно отправленных (с подтверждением).

## 6. Камера и профили — КРИТИЧЕСКИЙ раздел

Цель — побитово воспроизводимые условия съёмки. Требуется **полностью ручная**
съёмка с блокировкой всей автоматики.

### 6.1. Требования к устройству
- Камера должна поддерживать `REQUEST_AVAILABLE_CAPABILITIES_MANUAL_SENSOR` и
  `MANUAL_POST_PROCESSING`. Проверять на старте; если нет — предупредить, что
  идентичность не гарантируется, работать в ограниченном режиме.

### 6.2. Параметры профиля (минимум)
| Параметр | Camera2 key | Отключение авто |
|---|---|---|
| Выдержка (экспозиция) | `SENSOR_EXPOSURE_TIME` (нс) | `CONTROL_AE_MODE = OFF` |
| ISO (усиление) | `SENSOR_SENSITIVITY` | `CONTROL_AE_MODE = OFF` |
| Баланс белого | `COLOR_CORRECTION_MODE = TRANSFORM_MATRIX` + `COLOR_CORRECTION_GAINS` (и/или температура) | `CONTROL_AWB_MODE = OFF` |
| Фокус | `LENS_FOCUS_DISTANCE` | `CONTROL_AF_MODE = OFF` |
| Доп. параметры | любые из Camera2, влияющие на итог (напр. `SENSOR_FRAME_DURATION`, `TONEMAP_MODE`, стабилизация OFF) | — |

Обязательно в каждом `CaptureRequest`:
`CONTROL_MODE = OFF` (или `AUTO` c явными AE/AWB/AF = OFF по отдельности —
выбрать по совместимости), `CONTROL_AE_MODE = OFF`, `CONTROL_AWB_MODE = OFF`,
`CONTROL_AF_MODE = OFF`.

### 6.3. Профили (persist)
- Минимум два независимых сохраняемых профиля: «**Дневной свет**» и
  «**УФ-освещение**». Хранятся **глобально** для всего приложения (DataStore),
  переживают перезапуск.
- Экран тонкой настройки параметров камеры отдельно (меню «Профили камеры»).

### 6.4. Автоприменение (поведение в §5.4)
- Начало съёмки нового стола → профиль «Дневной свет».
- Переключение на «УФ» → мгновенно применить профиль «УФ».
- «Новый стол» → авто-сброс на «Дневной свет».
- Применение профиля = пересборка `CaptureRequest` на существующей сессии
  **без перезапуска камеры** (требование производительности — без задержек).

### 6.5. Съёмка
- Формат: **JPEG максимального качества** (опц. — DNG/RAW, если поддерживается;
  вынести в бэклог). Без пост-обработки, искажающей цвет.
- Сохранять рядом с фото снимок применённого профиля (для аудита идентичности).

## 7. Локальное хранилище (Room)

Сущности (черновая схема — уточнить при реализации):

```kotlin
@Entity data class Drilling(         // Долбление
  @PrimaryKey val id: String,        // UUID, он же id AnalysisSource на сервере
  val title: String,                 // название серии/долбления
  val passportJson: String,          // произвольные паспортные поля (JSON)
  val createdAt: Long,
  val syncStatus: SyncStatus,        // NOT_SENT / SENDING / SENT / ERROR
  val remoteId: String?,             // id проекта на s900 (== id при создании)
  val lastError: String?
)

@Entity data class Table(            // Стол
  @PrimaryKey val id: String,        // UUID
  val drillingId: String,            // FK → Drilling
  val number: Int,                   // №1, №2 ...
  val stackUid: String               // UUID, → attributes.stackUid обоих слоёв
)

@Entity data class Layer(            // Слой (снимок)
  @PrimaryKey val id: String,        // UUID
  val tableId: String,               // FK → Table
  val lampType: LampType,            // DAYLIGHT / UF
  val filePath: String,              // путь во filesDir
  val cameraProfileJson: String,     // снимок применённого профиля
  val capturedAt: Long,
  val remoteImageId: String?         // id SourceImage после заливки
)
```

Правила: каскадное удаление (Долбление → Столы → Слои + файлы). Индикация
занятого места. Корректная работа при большом числе снимков. Надёжность:
данные не теряются при закрытии/перезагрузке до успешной отправки.

## 8. Интеграция с сервером s900 (REST v3)

Всё ниже подтверждено по коду этого репозитория (`web/.../api/v3/s8/*`,
`s8-api/.../dto/*`). Общий справочник — `API.md`.

### 8.1. База и аутентификация
- Базовый URL: **`http://<host>:<port>/s8/api/v3/s8`** (context-path `/s8`).
  Пример: `http://192.168.0.10:8080/s8/api/v3/s8/analysis/source/{id}`.
- **HTTP Basic**, stateless: заголовок `Authorization: Basic base64("<user>:<pass>")`
  в каждом запросе. Только поверх HTTPS в проде (Base64 — не шифрование).
- ⚠️ **Текущее состояние сервера:** `SecurityConfig` закомментирован — v3 сейчас
  **без аутентификации**, проекты создаются под владельцем `anonymous`
  (`AnalysisSourceControllerImpl.createAnalysisSource`). Целевая модель — один
  технический пользователь `api` с правами только на свои проекты. **Открытый
  вопрос §10.3**: подтвердить с командой s900 финальную схему (Basic `api:secret`
  vs проверка логина/пароля конкретного пользователя s900, как просит бизнес-ТЗ).

### 8.2. Ключевые эндпоинты (используемые приложением)

| Метод | Путь (относит. `/api/v3/s8`) | Назначение |
|---|---|---|
| `POST` | `/analysis/source` | Создать долбление; body `AnalysisSourceDto` → `id` (идемпотентно по `id`) |
| `PUT` | `/analysis/source/{id}` | Обновить паспортные данные долбления |
| `GET` | `/analysis/source/{id}` | Прочитать проект (`AnalysisSourceDto`) |
| `GET` | `/analysis/source/{id}/fovs/size` | Кол-во столов (FieldOfView) |
| `POST` | `/analysis/source/{id}/image/file` | Залить кадр в **новый** стол (FieldOfView) → `id` изображения |
| `POST` | `/analysis/source/{id}/fov-idx/{fovIdx}/image/file` | Залить кадр в **существующий** стол по индексу |
| `POST` | `/analysis/source/{id}/fov/{fid}/image/file` | То же по id стола |
| `PUT` | `/analysis/source/{id}/image/{iid}` | Обновить метаданные кадра (`SourceImageDto`, в т.ч. `attributes.lampType`, `stackUid`, `coreImageType`) |
| `PUT` | `/analysis/source/{id}/fov-idx/{fovIdx}/image-idx/{imageIdx}/file` | Залить/заменить файл + метаданные (`file` **или** `file-id`, опц. `source-image`); дергает авто-стек |
| `POST` | `/upload/file-id` → `PUT /upload/append/file/{fileId}` | Чанковая загрузка больших файлов (октет-стрим), затем ссылка `file-id` |

Загрузка файлов — `multipart/form-data`, часть `file` (`MultipartFile`).
Поддерживаются только изображения (проверка расширения на сервере).

### 8.3. Рекомендуемая последовательность отправки одного стола

Для каждого стола (пара Дневной+УФ), последовательно:

```
1. (один раз на долбление) POST /analysis/source
   body: {"id": "<uuid>", "title": "<название>",
          "field": "...", "well_number": "...", "wellbore": "...",
          "perforation_number": 12, "core_recovery": 4.8, ...   ← гео-атрибуты §8.5
          "app_version": "kern-android/1.0",
          "postupload_processing": true}                        ← см. §10.5
   → 200, id проекта. Идемпотентно: повторный POST с тем же id вернёт id.
   (гео-атрибуты — плоские ключи верхнего уровня, попадают в attributes через
    @JsonAnySetter; НЕ вкладывать в отдельный объект.)

2. POST /analysis/source/{id}/image/file           (multipart file = дневной JPEG)
   → daylightImageId, создан НОВЫЙ FieldOfView (стол).

3. fovIdx = GET /analysis/source/{id}/fovs/size − 1
   (надёжнее: GET /analysis/source/{id} и найти FieldOfView, содержащий
    daylightImageId — не зависит от гонок индекса.)

4. PUT /analysis/source/{id}/image/{daylightImageId}
   body SourceImageDto: {"attributes": {"lampType": "DAYLIGHT",
        "stackUid": "<stack_uid стола>", "coreImageType": "..."}}

5. POST /analysis/source/{id}/fov-idx/{fovIdx}/image/file   (multipart file = УФ JPEG)
   → ufImageId  (тот же стол/FieldOfView)

6. PUT /analysis/source/{id}/image/{ufImageId}
   body: {"attributes": {"lampType": "UF", "stackUid": "<тот же stack_uid>", ...}}
```

Столы одного долбления заливать **последовательно** (шаг 3 полагается на «стол =
последний FieldOfView»; при параллельной заливке индекс «поедет»). Для больших
файлов — чанковый Upload API (§8.2) + `PUT …/image-idx/{imageIdx}/file` с
`file-id` и частью `source-image` (метаданные одним вызовом).

### 8.4. DTO (JSON) — точные имена полей

`AnalysisSourceDto` (`s8-api/.../dto/AnalysisSourceDto.java`): `id`, `title`,
`user` (сервер проставляет сам — клиент не задаёт), `created`/`modified` (long,
мс), `storageId`, `fieldOfViews[]`. **Любые прочие ключи → `attributes`**
(`@JsonAnySetter`) — сюда кладём паспортные поля произвольной схемы.

`SourceImageDto`: `id`, `idx`, `title`, `type`, `pixelSize`, `physUnits`,
`dimX`, `dimY`, `attributes` (объект `ImageAttributesDto`), …

`ImageAttributesDto` (важные для нас поля):
- `lampType` — `"DAYLIGHT"` | `"UF"`.
- `stackUid` — строка-UID, группирует слои одного стола в стек (сериализуется как
  `stack_uid` в сущности).
- `coreImageType` — `"UNKNOWN"` | `"CIRCULAR"` | `"LONGITUDINAL_CUT"` |
  `"SURFACE"`.
- опц.: `kernDiameter`, `kernUpperDepth`, `kernLowerDepth`, `pixelSize`,
  `physUnits`.

### 8.5. Паспортные поля — КОНКРЕТНАЯ гео-схема (подтверждено по коду)

Паспортные поля долбления — это **фиксированный набор гео-атрибутов**
`AnalysisSource`, по которым фотокнига/каротаж керна ищет и раскладывает данные
(`AttrUtil`, `WellLogCoreService.findAnalysisSourcesIdsByCriteria`). Каптионы —
из `ui_ru.xml`. Приложение шлёт их как плоские ключи в `POST/PUT /analysis/source`.

| Ключ (JSON) | Тип | Каптион (RU) | Назначение |
|---|---|---|---|
| `field` | String | Месторождение/площадь | ключ поиска керна |
| `well_number` | String | Номер скважины | ключ поиска |
| `wellbore` | String | Ствол | ключ поиска |
| `perforation_number` | Integer | **Номер долбления** | ключ поиска; = app-«Долбление» |
| `core_recovery` | Double | Вынос керна, м. | паспорт |
| `depth_correction` | Double | Поправка, м. | привязка по глубине |
| `initial_sampling_reference_top` | Double | Исходная привязка отбора, кровля, м. | глубина |
| `initial_sampling_reference_bottom` | Double | Исходная привязка отбора, подошва, м | глубина |
| `title` | String | Название | заголовок проекта |

Плюс глубина **по столу/керну** (для раскладки в каротаже) — задаётся на
`SourceImage.attributes`: `kernUpperDepth`, `kernLowerDepth` (м), опц.
`kernDiameter` (мм). Пример из бизнес-ТЗ «Керн-456, 150–155 м» → `kernUpperDepth=150`,
`kernLowerDepth=155` на слоях этого стола. **Открытый вопрос §10.6** — где глубина
авторитетна (на керне) и как её вводит оператор (диапазон на стол).

**Про «загрузку конфигурации с сервера».** Источник схемы на сервере — список
`AttrUtil.getAttributeList()` (дефолтные `CORE_*` + пользовательские из
`S8_DATA_DIR/attributes.json`, зависят от языка). **REST-эндпоинта, который его
отдаёт, пока НЕТ** — см. §10.1. Поэтому:
- **MVP:** зашить в приложение эту гео-схему как встроенный дефолт (полный режим
  паспортизации работает без сервера).
- **Упрощённый режим** (по бизнес-ТЗ): если оператор пропускает поля — слать
  только `title`; остальное дозаполняется в s900.
- Когда сервер добавит эндпоинт — подгружать/расширять схему динамически
  (в т.ч. кастомные атрибуты из `attributes.json`).

### 8.6. Как s900 читает залитый керн (для сверки)
Обратная сторона контракта (наш экспорт должен ей соответствовать):
`GET /core/{idk}/image/lamptype/{DAYLIGHT|UF}` (`CoreController`) и
`GET /well/log/core/{coreId}/image?...&lampType=...&coreImageType=...`
(`WellLogCoreController`) выбирают кадр из `FieldOfView` по
`attributes.lampType` (+ `coreImageType`). То есть корректно заполненные
`lampType`/`coreImageType` на каждом `SourceImage` — обязательны, иначе слой не
найдётся при чтении.

## 9. Очередь отправки и надёжность

- Пакетная отправка **целыми долблениями** (все столы и слои), не отдельными
  фото.
- **WorkManager**: одна задача на долбление, `setConstraints(NetworkType.CONNECTED)`,
  экспоненциальные ретраи. Статусы `NOT_SENT/SENDING/SENT/ERROR` в Room,
  прогресс в UI.
- При обрыве — данные остаются локально, возможен повтор неудачных.
- Идемпотентность: `POST /analysis/source` идемпотентен по `id`; повторную
  заливку слоёв защищать по `remoteImageId` (не слать уже залитое).
- Обработка на сервере — «аналогично загрузке из сканера **GEO 360**»
  (бизнес-ТЗ). Детали ингестии стека — **у Губарева Семёна** (§10.2).

## 10. Открытые вопросы к команде s900 (до/во время реализации §8–9)

1. **Эндпоинт конфигурации паспортных полей.** Схема на сервере уже есть в виде
   `AttrUtil.getAttributeList()` (дефолт `CORE_*` + `attributes.json`), но
   **REST-эндпоинта, отдающего её, нет**. Нужен GET, возвращающий список полей
   (id, тип, каптион, обязательность), чтобы строить форму динамически. До этого
   — встроенная гео-схема §8.5.
2. **Ингестия стека керна = «как GEO 360».** Подтвердить у **Семёна Губарева**
   точный контракт: (а) достаточно ли последовательности §8.3 с
   `lampType`/`stackUid`/`coreImageType`, или есть выделенный эндпоинт ингестии;
   (б) **как пара Дневной+УФ становится стеком** на сервере. Важно:
   авто-простановка `FieldOfViewType.STACK`
   (`setFieldOfViewTypeStackIfNecessary`) срабатывает только для XPL-изображений
   (`isXplLike`), а **не** для lamp/core-кадров — значит для керна тип стека
   ставится иначе (импорт GEO 360 / группировка по `stack_uid` / post-upload).
   Уточнить.
3. **Аутентификация.** Финальная схема доступа (§8.1): `SecurityConfig` сейчас
   выключен. Бизнес-ТЗ просит проверять логин/пароль пользователя s900 —
   подтвердить, будет ли это Basic под техпользователем `api` или
   пер-пользовательская проверка, и как это влияет на владельца проекта.
4. **Владелец проекта.** Сейчас проекты создаются как `anonymous`. Как они
   должны атрибутироваться к оператору/организации?
5. **Триггер post-upload-обработки.** Атрибут `postupload_processing` (boolean)
   отслеживается сервером (`PostUploadWatchingWindow`, `ProjectTitleLayout`).
   Подтвердить: должен ли клиент выставлять его, чтобы сервер запустил построение
   `Core` из `FieldOfView` (фотокнига керна)? Как клиент узнаёт, что обработка
   завершилась/успешна?
6. **Авторитет глубины и её ввод.** Каротаж раскладывает керн по глубине
   (`Core.minDepth`/`maxDepth`, `kernUpperDepth`/`kernLowerDepth`). Подтвердить,
   откуда сервер берёт глубину стола (из `kernUpper/LowerDepth` слоёв? из
   `initial_sampling_reference_*`?) и как оператор её задаёт (диапазон «от–до» на
   каждый стол в UI съёмки?).
7. **Масштаб/`pixelSize` (мкм/пиксель).** Каротаж/фотокнига используют `pixelSize`
   и `physUnits` для корректного рендеринга размеров. Телефон не знает физический
   масштаб керна. Уточнить: (а) обязателен ли `pixelSize` для фотокниги, (б)
   нужна ли калибровка на клиенте (эталон/линейка/известный диаметр керна в
   кадре), либо сервер вычисляет масштаб сам. Влияет на камеру и на форму стола.

## 11. Нефункциональные требования (из бизнес-ТЗ)

- **Идентичность изображения (критично)** — §6: профили применяются побитово
  одинаково от сессии к сессии.
- **Автосохранение** — без явной кнопки «Сохранить»; сохранение при выходе с
  экрана съёмки/галереи.
- **Надёжность** — данные (фото + метаданные) хранятся локально до успешной
  отправки; защита от потери при закрытии/перезагрузке.
- **Производительность** — мгновенное применение профиля без перезапуска камеры;
  быстрый переход список→галерея→досъёмка; быстрые превью и переключение слоёв
  при большом числе столов.
- **Хранение** — эффективное управление памятью, индикация занятого места,
  очистка отправленных долблений (с подтверждением), корректная работа с большим
  числом снимков.

Итеративно: каждый этап — самостоятельный PR, заканчивается **запускаемым**

**Легенда трудоёмкости:** S ≈ 1–2 дня, M ≈ 3–5 дней, L ≈ 1–2 недели (оценки
ориентировочные, 1 разработчик).

- DoD: приложение собирается и запускается, навигация между пустыми экранами
  работает.

### Этап 1 — Камера и профили (ядро ценности) · L 🔴 риск
- Задачи:
  - `CameraController` на **Camera2**: открытие, превью (`SurfaceView`/`TextureView`),

  - Проверка `MANUAL_SENSOR` + `MANUAL_POST_PROCESSING`; graceful-деградация и

  - Модель `CameraProfile` (exposureTime, iso, wbGains/temp, focusDistance,

  - Экран **Съёмка** (§5.4): счётчик «Стол №N», переключатель Дневной⇄УФ с

## 13. Правила для Claude Code (в Android-проекте)

- Домен именовать по §2: `Drilling` (Долбление), `Table` (Стол), `Layer` (Слой),
  `CameraProfile`.

  `web/.../api/v3/s8/*`, `s8-api/.../dto/*`, `API.md`; при сомнениях —
  зафиксировать как открытый вопрос (§10), а не угадывать.
- **Дизайн — по §14** (палитра/типографика/компоненты navy-темы s900). Не

### 14.3. Типографика
- Шрифт: **Lato** (брендовый шрифт s900; подключить Lato TTF, напр. из Google
  Fonts). Фолбэк — системный sans-serif.
- Шкала (токены `BODY1..BODY4` из `NavyLayout`): **BODY1 = 18sp**, **BODY2 =
  16sp**, **BODY3 = 14sp**, **BODY4 = 12sp**; для каждого есть `*_BOLD`.
- Правило: размер шрифта задаётся только шкалой (не произвольные значения).
  Заголовки экранов — BODY1_BOLD, тело — BODY2/BODY3, подписи/каптионы — BODY4.

### 14.4. Отступы, радиусы, тени
- **Спейсинг** — именованная шкала `XS/SM/MD/LG/XL` (как в navy: 4/8/12/16/24dp
  ориентировочно). Использовать `GAP_*`, `PADDING_*`, `MARGIN_*` по имени, не
  «магические» пиксели.
- **Радиусы:** `2dp` (мелкие чипы/инпуты), `4dp` (кнопки/карточки — основной),
  `8dp` (крупные карточки/модалки), `pill` (полное скругление для бейджей/
  переключателей).
- **Тени:** минимальные. Карточка — почти плоская (граница `gray_20` вместо тени
  или тень `0 1px 2px rgba(0,0,0,0.1)`); модалка/диалог — `0 0 20px
  rgba(0,0,0,0.25)`.

### 14.5. Компоненты
- **Кнопки:**
  - *Primary* — заливка `blue #0060AA`, текст белый, радиус 4dp, высота ≥48dp,
    нажатие `blue_dark #004A84`, disabled `gray_20`.
  - *Secondary* — белый фон, граница `blue`, текст `blue`.
  - *Danger* — текст/граница `red_30` (удаление), заливка `red_10` при
    подтверждении.
- **Карточка долбления** (§5.2) — белая, граница `gray_20`, радиус 8dp; заголовок
  `black BODY2_BOLD`; строка статуса — **бейдж** (см. ниже).
- **Бейдж статуса отправки** — pill, BODY4:
  | Статус | Текст | Фон |
  |---|---|---|
  | Не отправлено | `gray_40` | `gray_10` |
  | Отправляется | `blue` | `blue_10` + линейный прогресс `blue` |
  | Отправлено | `green_30` | `green_10` |
  | Ошибка | `red_30` | `red_10` |
- **Карточка стола** (§5.5) — превью Дневного (16:9/квадрат), радиус 8dp; поверх —
  номер «Стол №N» (`black` на белой плашке) и **бейдж «УФ»** (жёлтый `#FFEF00`
  чип, если есть УФ-слой).
- **Переключатель Дневной ⇄ УФ** — сегмент-контрол (pill): активный сегмент
  `blue` (Дневной) / тёмно-фиолетовый или `gray_50` c жёлтой меткой (УФ),
  неактивный — прозрачный/`gray`. Крупный, для работы в перчатках.
- **Поля формы паспорта** (§5.3) — фон `gray_10`, граница `gray_20`, фокус —
  граница `blue`; ошибка — граница `red_30` + подпись `red_30 BODY4`; лейбл
  `gray_40 BODY4`.
- **Прогресс отправки** (§5.6) — линейный индикатор `blue` на `blue_10`.

### 14.6. Иконки
Монохромные линейные иконки (navy использует icon-font `ThemeIcons`/`NavyIcons`).
Для Android — **Material Symbols (Outlined)**, одноцветные, цвет наследуют от
контекста (`blue` для действий, `gray_40` для нейтральных). Не использовать
разноцветные/растровые иконки.

### 14.7. Тёмный экран съёмки (важное UX-решение)
Экран **Съёмки** (§5.4) и **Просмотра стола** — на тёмном фоне (`black #0B1524`
/ `gray_50`), т.к.: (1) фотокабина затемнена, светлый UI слепит; (2) тёмное
окружение не искажает восприятие цвета образца в кадре. HUD-элементы (счётчик
стола, параметры камеры, переключатель) — светлый текст/иконки поверх тёмного,
акцент `blue`. Остальные экраны — светлая navy-тема.

### 14.8. Реализация в Android (Material 3 + Compose)
Обернуть Material 3 в кастомную тему `KernTheme`; цвета — как токены:
