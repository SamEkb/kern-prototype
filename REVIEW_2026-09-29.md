## 1. Соответствие требованиям

| Пакетная отправка, очередь и прогресс | WorkManager, одна задача на долбление, прогресс по столам, ретраи | Основа есть; повторная отправка некорректна в ряде сценариев |

## 2. Подтверждённые дефекты и дополнительные риски

### R01 — P1. Метаданные пропускаются после сбоя и при последующем редактировании

**Место:** `K/sync/DrillingUploader.kt:85,96,102`, `K/data/KernRepository.kt:184`.

После POST файла uploader сразу сохраняет `remoteImageId`, затем делает PUT метаданных. Если PUT упал, при повторе слой с заполненным ID проходит через `continue` и больше никогда не получает `lampType`, `stackUid`, глубины. Аналогично изменение глубин уже отправленного слоя помечает долбление dirty, но повторный экспорт пропускает PUT этого слоя. В обоих случаях финальный статус может стать SENT при неполных/устаревших метаданных.

**Устранение:** различать стадии «файл принят» и «метаданные подтверждены», учитывать ревизию метаданных. Существующий файл не загружать повторно, но недоставленный/изменившийся PUT выполнять. **Минимум для MVP:** сохранять ID сразу после успешного POST, отдельно хранить признак подтверждения метаданных; сбрасывать его при изменении метаданных и при повторе выполнять недоставленный PUT. Правки во время отправки блокировать по R05. Простое перенесение записи ID после PUT неправильно: при сбое PUT потеряется информация об уже загруженном файле и возникнет дубль. Для очистки глубин также согласовать способ явного удаления значения: глобально установлен `explicitNulls=false`, поэтому `null` сейчас не попадает в JSON.

**Проверка:** прервать именно PUT после успешного POST, затем повторить; отдельно изменить и очистить глубину уже отправленного стола. На сервере должен остаться один файл слоя с актуальными метаданными.

### R02 — P1. Отсутствующие JPEG молча исключаются из отправки

**Место:** `K/sync/DrillingUploader.kt:79,73`.

`filter { File(it.filePath).exists() }` скрывает отсутствие файла, пустой стол просто пропускается. Затем долбление получает SENT. Это скрывает повреждение архива, а пользователь может удалить локальные данные через «Очистить отправленные».

**Устранение:** проверять состав экспорта и целостность файлов, выдавать ошибку с указанием стола/слоя, не выставлять SENT при пропущенных локальных данных. Уже подтверждённые сервером слои оценивать по подтверждённому состоянию, а не только по наличию файла. Отдельно согласовать допустимость пустого долбления и неполной пары: неполная пара сама по себе не равна повреждению файла.

**Проверка:** отсутствующий JPEG, нулевой файл и повреждённый JPEG должны давать понятную ошибку без ложного SENT.

### R03 — P1. Смена сервера или удаление серверного проекта ломает повторную отправку

**Место:** `K/sync/DrillingUploader.kt:58,85`; `LayerEntity`, `DrillingEntity`; `SessionLoginInterceptor.intercept()`.

При 404 на PUT проект создаётся заново, но старые `remoteImageId` сохраняются. Uploader ищет их в новом проекте, не находит и всё равно выполняет `continue`. Новый сервер получает проект без прежних изображений, клиент — SENT. Идентификаторы не привязаны к серверу. Кроме того, адрес из DataStore читается для каждого запроса: смена настроек во время работы может разделить одну отправку между двумя серверами.

**Устранение:** хранить идентичность назначения вместе с состоянием экспорта; фиксировать её на всю задачу. После пересоздания проекта сверять/сбрасывать состояния его слоёв и отправлять их заново. Изменение назначения должно запускать отдельный согласованный экспорт.

**Проверка:** отправить на A, переключить на B; отдельно удалить проект на A и повторить. Все слои должны присутствовать в новом проекте.

### R04 — P1. Пересъёмка и удаление не синхронизируют существующее серверное содержимое

**Место:** `K/data/KernRepository.kt:170`, `K/sync/DrillingUploader.kt:76`, `K/network/S900Api.kt`.

Пересъёмка обнуляет ID слоя, но старый серверный файл остаётся. Если переснят DAYLIGHT, он обрабатывается первым и создаёт новый FoV, поскольку `fovIdx` ещё неизвестен. Сохранённый UF затем пропускается; пара может оказаться в разных FoV. Если переснят UF при существующем DAYLIGHT, новый UF добавляется в прежний FoV рядом со старым. Для локального удаления слоя/стола нет ни серверной операции, ни журнала удалений. Перенумерация меняет только локальный порядок: номер стола отсутствует в передаваемом DTO.

**Устранение:** сначала определить удалённый стол по любому известному слою/стабильному ID; согласовать операции замены и удаления с S900, хранить необходимые ссылки и журнал изменений. Уточнить, является отправка обновлением проекта или созданием версии архива. Если удаление локально означает только очистку устройства, это должно быть отдельным действием с явной семантикой. Номер стола передавать в согласованном поле, не придумывать ключ API.

**Проверка:** поочерёдно переснять DAYLIGHT и UF уже отправленной пары, удалить слой, переименовать номер. Проверить количество FoV, актуальных слоёв и видимый номер в S900.

### R05 — P1. Редактирование во время отправки теряет состояние «изменено»

**Место:** `K/sync/DrillingUploader.kt:38,73`, `K/data/KernRepository.kt:199`, `LayerDao.setRemoteImageId()`.

Uploader работает со снимком содержимого на момент старта. Repository сбрасывает статус только для SENT/ERROR, но не SENDING. Оператор может доснять/изменить данные, пока отправляется старое содержимое, после чего uploader безусловно ставит SENT. Ещё хуже при пересъёмке: локальный ID слоя сохраняется; ответ старого POST может записать ID старого серверного изображения уже в новую версию слоя.

**Устранение:** ревизии долбления и слоя, условная фиксация ответа по конкретной ревизии; SENT только если текущая ревизия совпадает с отправленной. Простой первый вариант — блокировать редактирование/удаление конкретного долбления на время передачи, но ограничения должны действовать и в repository. Отмену worker обрабатывать отдельно от обычной ошибки. `ExistingWorkPolicy.REPLACE` требует проверки, что старая отменяемая задача больше не меняет состояния новой.

**Проверка:** медленная отправка → изменение паспорта, глубины, пересъёмка/добавление слоя. Неотправленные изменения не должны получать SENT и ID старого файла.

### R06 — P1. Нет полной идемпотентности загрузки изображения

**Место:** `DrillingUploader.uploadTable()` — POST изображения и следующая локальная запись ID.

Если сервер принял JPEG, но ответ потерялся или процесс завершился до `setRemoteImageId`, следующий запуск повторяет POST и создаёт ещё один файл/FoV. Наличие `remoteImageId` защищает только уже зафиксированные ответы. `stackUid` назначается отдельным последующим запросом, поэтому сам по себе эту неопределённость не устраняет. Фолбэк на «последний FoV» также не гарантирует правильной привязки при параллельной работе другого клиента.

**Устранение:** согласовать серверный ключ идемпотентности/клиентский ID слоя либо протокол поиска принятой операции. Не заявлять гарантию «без дублей», пока нет восстановления после потери ответа. Для FoV использовать надёжный идентификатор и подтверждённый ответ вместо догадки по размеру списка.

**Вариант восстановления без изменения сервера (проверить на S900):** multipart уже передаёт имя JPEG с UUID. Если сервер сохраняет исходное имя в `SourceImage.title` или другом доступном поле, после потери ответа можно искать принятую версию файла и восстанавливать её ID. Проверить точность имени, полноту выдачи, момент видимости результата и несколько совпадений. Поиск перед POST не гарантирует идемпотентность: первый запрос может ещё выполняться, GET вернёт пусто, второй POST создаст дубль. При неопределённом результате не повторять POST вслепую.

Ключ поиска должен обозначать конкретную версию снимка. При пересъёмке ID записи слоя сохраняется, а новый JPEG получает новый UUID в имени: нельзя автоматически подставлять ID записи вместо имени реально отправленного файла.

**Приоритет:** P1 для эксплуатации с обещанием повторов без дублей; P2 допустим для согласованного пилота с ручной сверкой. Частота сбоя не измерена, считать его заведомо редким оснований нет.

**Проверка:** разорвать соединение после серверного сохранения POST, до получения ответа клиентом; повторить после перезапуска процесса. Отдельно проверить позднее завершение первого POST и видимость файла при поиске по имени.

### R07 — P1. Миграция БД допускает потерю всего локального каталога

**Место:** `K/di/DatabaseModule.kt:24`, `K/data/db/KernDatabase.kt` (версия 3).

Используется `fallbackToDestructiveMigration(dropAllTables = true)`, миграции не зарегистрированы. При обновлении с несовместимой старой схемы Room может удалить таблицы с долблениями, столами и слоями. JPEG во `filesDir` не восстанавливают утраченные связи и паспортные данные автоматически.

**Устранение:** явные миграции поддерживаемых версий, сохранённые схемы Room и проверка обновления реального архива. Разрушительный fallback не использовать для пользовательских данных. Не удалять автоматически все файлы без записей в БД: после сбоя или разрушительной миграции это могут быть единственные сохранившиеся снимки. Сначала восстановление/карантин; уборка только для доказанно ненужных файлов.

**Проверка:** установить новую версию поверх каждой поддерживаемой старой с неотправленной парой и паспортом; проверить ID, связи, файлы и возможность отправки.

### R08 — P1. Пересъёмка удаляет предыдущий кадр до надёжной фиксации нового

**Место:** `K/data/KernRepository.kt:149,158`; `CaptureViewModel.capture()`.

Старый JPEG и thumbnail удаляются до создания миниатюры и `layerDao.upsert`. Сбой/отмена между этими шагами оставляет старую запись БД со ссылкой на удалённый файл, а новый JPEG — без записи. Создание стола, запись слоя и dirty-статуса тоже не составляют одну транзакцию. Ошибка первого снимка оставляет пустой стол; незавершённые файлы не очищаются протоколом восстановления.

**Устранение:** новый файл записывать отдельно, проверять успешность записи; затем транзакционно переключать запись слоя/стола и dirty-ревизию; старые файлы удалять после commit. Для сбоя процесса предусмотреть временные файлы и безопасную уборку сирот. Обычная транзакция Room не делает файловую систему транзакционной.

**Проверка:** остановки процесса и имитация нехватки места до записи JPEG, после JPEG, до/после DB commit. До успешной фиксации новый кадр не должен уничтожать старый.

### R09 — P1. Ошибка получения кадра может сохраняться как успешный снимок

**Место:** `app/src/main/jni/jnicam.cpp`, `pullInto()`; `K/camera/ToupcamController.kt:337–338,180`.

При ошибке `Toupcam_PullStillImageV2` JNI пишет лог и возвращается через `void`, не обновляя bitmap. Kotlin безусловно завершает ожидание с `Result.success(Unit)` и сохраняет переиспользуемый буфер — возможен старый либо пустой кадр под новым столом. Аналогично теряется результат `snap()`, а Boolean результата `Bitmap.compress()` не проверяется. Ошибки FFC также скрыты.

**Устранение:** передавать ошибки всего пути SDK → JNI → Kotlin; успешным считать только получение нового кадра и успешную запись валидного файла. При обязательном FFC не переходить молча к некорректированному снимку. Сохранять диагностические данные кадра и применения профиля.

**Проверка:** сбой pull после предыдущего успешного кадра, ошибка Snap, отключение USB и ошибка записи не должны создавать новый успешный слой.

### R10 — P1. Гонка профиля шире, чем описано в FIXES §7

**Место:** `K/viewmodel/CaptureViewModel.kt:113,138,152–153`; `K/camera/ToupcamController.kt:117`.

Подтверждена запись по `_lamp.value`, прочитанному после ожидания снимка. При этом `tableId` уже захвачен в локальную `var`: «Новый стол» не переносит этот кадр в новый стол, но сбрасывает освещение на DAYLIGHT и может привести к замене дневного слоя старого стола. Дополнительно `switchLamp()` сразу меняет UI, но загружает и применяет профиль асинхронно. Нажатие «Снять» сразу после переключения может снять старым профилем, даже если переключение во время самого снимка запретить. В контроллере `currentProfile` обновляется до выполнения SDK-сеттеров; capture может получить новый JSON профиля при ещё старых настройках камеры.

**Устранение:** сериализовать переключение, применение и съёмку одной операционной очередью/блокировкой; фиксировать стол, освещение и подтверждённую версию профиля до Snap. Состояние Ready для съёмки должно означать завершённое применение нужного профиля. Если SDK применяет настройки с задержкой кадра, дождаться подтверждения/кадра с нужными параметрами. Блокировать UI, но не полагаться только на UI.

**Проверка:** мгновенный спуск после DAYLIGHT → UF, быстрые многократные переключения, новый стол во время снимка. Проверять и метку слоя, и фактическую экспозицию/WB, и JSON профиля.

### R11 — P1. Эталон FFC изменяет сохранённый профиль без его сохранения

**Место:** `K/camera/ToupcamController.kt:198,235,237`; `CameraProfilesViewModel.confirmFfc()`; `ProfileTransfer.importJson()`.

Эталон всегда записывается в `ffc/ffc_DAYLIGHT.png` или `ffc_UF.png`. Если профиль уже ссылается на этот путь, пересъёмка эталона немедленно меняет данные сохранённого профиля, даже если выйти без «Сохранить». Исторические JSON кадров тоже содержат тот же изменяемый путь и не позволяют восстановить прежнюю коррекцию. Импорт переписывает файл по тому же пути, а кэш контроллера проверяет только путь. Однако сейчас экран съёмки получает новый экземпляр контроллера, поэтому устаревший кэш после импорта не считается подтверждённым дефектом текущего сценария. Этот риск станет актуальным при переиспользовании контроллера/переходе к единой сессии (R19). Импорт нескольких профилей не атомарен — сбой второй записи оставляет первый уже заменённым.

**Устранение:** минимум для MVP — сохранять эталон под новым уникальным именем (UUID либо метка времени с защитой от совпадений), не перезаписывая файл подтверждённого профиля; менять ссылку только при сохранении. Это правило обязательно и для пересъёмки в `captureFfcReference()`, и для импорта в `ProfileTransfer.importJson()`: обе операции создают новые файлы и не перезаписывают подтверждённые эталоны. Для расширенного аудита — неизменяемые версионированные эталоны с хешем; сначала staging, затем подтверждённое переключение профиля на новую версию. Полностью проверять bundle, версию, диапазоны и PNG до изменений. Инвалидировать кэш по версии/хешу. Явно сообщать отсутствие эталона при экспорте/съёмке вместо молчаливого пропуска.

**Проверка:** переснять FFC и выйти без сохранения; импортировать другой PNG с тем же типом освещения; подать повреждённый второй профиль. Старая подтверждённая конфигурация должна оставаться целой.

### R12 — P2. Проверка соединения не доказывает авторизацию

**Место:** `K/network/ConnectionTester.kt:51`, `SessionLoginInterceptor` и `InMemoryCookieJar`.

Любой ответ кроме auth-редиректа и 5xx считается Success, включая 401/403. Ответ логина игнорируется. В основной отправке наличие cookie принимается за рабочую сессию; 401/403 не инициируют обновление сессии, ошибки login подавляются. При смене учётной записи cookie не очищается, поэтому запросы могут продолжить идти от старого пользователя. CookieJar не проверяет срок, path и Secure; сессия логируется целиком через `Set-Cookie` (`SessionLoginInterceptor.kt:83–86`). Это конкретные дефекты реализации, а не требование отказаться от HTTP, которое допускается ТЗ.

**Устранение:** разделить доступность сервера и авторизацию, проверять согласованный результат login и защищённый API; корректно обрабатывать 401/403, ограничить повтор входа. Сбрасывать/разделять сессии при смене аккаунта и назначения, фильтровать cookies по URL и сроку, убрать значения сессионных токенов из логов. Не считать произвольный 404 подтверждением личности.

**Проверка:** неверный пароль, 401, 403, истёкшая сессия, смена пользователя A → B, смена HTTPS → HTTP, параллельные отправки.

### R13 — P2. Автопроцедуры редактора конкурируют с переключением и ручными настройками

**Место:** `CameraProfilesScreen.kt:222,233,293`, `CameraProfilesViewModel.selectLamp()/runAutoExposure()/confirmFfc()`, `ToupcamController.autoExposure()`.

`busy` блокирует только кнопки запуска процедур. Переключатель профиля, слайдер, импорт, сохранение и выход остаются доступны. Результат AE/AWB может вернуться после смены выбранной лампы и заменить `_working` старым профилем. При FFC путь одной лампы может записаться в рабочий профиль другой. Слайдер параллельно вызывает applier и выключает AE. У `autoExposure()` нет `finally` для отключения автоматики при отмене на `delay`.

**Устранение:** блокировать конфликтующие действия и в VM, и в UI; операции привязывать к ID/ревизии профиля; отбрасывать устаревший результат. При отмене/ошибке гарантированно возвращать ручной режим и валидное состояние камеры. Кнопки запуска разрешать только при реально готовой камере: сейчас `manualSupported` по умолчанию true даже при отсутствии Ready.

**Проверка:** AE → смена лампы/движение слайдера/назад; FFC → смена лампы; запуск процедуры без подключённой камеры.

### R14 — P2. Отображаемые и сохранённые параметры не равны применённым

**Место:** `CameraProfilesScreen.kt:76–117`, `ToupcamProfileApplier.apply()`, `ToupcamController.capture()`.

UI предлагает gain от 25, но applier ограничивает минимумом 100; snapshot сохраняет исходный профиль. Например, пользователь видит и сохраняет 25, а SDK получает 100. AE допускает выдержку до 1000 мс, ползунок — только до 500 мс. Диапазоны захардкожены, хотя дополнительные требования требуют получать их у камеры. SDK-сеттеры и readback не проверяются, а `manualSupported=true` задан без проверки возможностей.

**Устранение:** читать поддерживаемые диапазоны (`get_ExpTimeRange`, `get_ExpoAGainRange` доступны в локальном SDK), валидировать профиль, отражать реально принятые значения и причины ограничений. Snapshot кадра должен различать запрошенные и подтверждённые параметры. Предупреждение об изменении сохранённого профиля сейчас показывается перед сохранением, тогда как дополнительные требования формулируют его перед применением изменений — это нужно согласовать.

### R15 — P2. Паспорт и глубины могут терять значения без ошибки

**Место:** `K/data/PassportCodec.kt:30,46`, `DrillingFormScreen`, `TableViewScreen.DepthEditor()`.

Невалидные числовые поля просто пропускаются кодеком. Например, `1,5` в INTEGER или `1..2` в DOUBLE исчезнут после сохранения без объяснения. `decodeToStrings()` пытается читать число даже из JSON-строки: `well_number="0012"` отображается как `12` и после сохранения теряет ведущие нули. Глубины без валидации преобразуют неправильный ввод в null; отношение верхней/нижней границ не проверяется.

Дополнительно глубина хранится отдельно на существующих слоях: если ввести её после DAYLIGHT, а UF доснять позже, новый UF получит null — `saveLayer()` наследует глубины только заменяемого слоя. Это нарушает согласованность глубины внутри стола.

**Устранение:** сохранять строковые идентификаторы без числовой нормализации, показывать ошибки полей, валидировать диапазон глубин. Общую глубину хранить на столе или гарантированно копировать во все его новые слои. Для паспорта/глубин обеспечить согласованное с ТЗ автосохранение и восстановление черновика.

**Проверка:** номер скважины `0012`, номер долбления `12а` после согласования строкового типа, неверные числа, ввод глубины до досъёмки UF, выход назад без нажатия Save/OK.

### R16 — P2. Восстановление камеры после отключения не реализовано внутри экрана

**Место:** `CaptureViewModel.start()`, `CameraProfilesViewModel.start()`, `ToupcamController.onSdkEvent()` и `releaseInternal()`.

Флаг `opened` ставится до успешного подключения и не сбрасывается при ошибке. При отключении SDK меняется только state, ресурс и флаг не переоткрываются. Повторное подключение USB не запускает восстановление в этих VM; требуется как минимум выход/повторный вход. `onSurfaceDestroyed()` очищает только ссылку VM, не поверхность контроллера. `releaseInternal()` останавливает handler без ожидания завершения работы и сразу освобождает bitmap — отдельный риск гонок, который нужно проверять на устройстве.

**Устранение:** явные состояния подключения/ошибки/повторного открытия, отделение Surface от владения камерой, сериализация завершения операций и освобождения буферов. Обработать уход в фон, возвращение, отмену разрешения и переподключение.

### R17 — P2. Размер полного кадра определяется по неверному списку разрешений

**Место:** `app/src/main/jni/jnicam.cpp`, `openDevice()/getStillSize()/snap()`.

`gStillIndex` выбирается из `Toupcam_get_ResolutionNumber/get_Resolution` (preview), затем применяется к `get_StillResolution` и Snap. SDK отдельно предоставляет `get_StillResolutionNumber/get_StillResolution` (`toupcam.h:311–312,801–802`). Совпадение списков для конкретной модели не проверяется. При ошибке чтения размера Kotlin сохраняет запасные 1920×1080, а JNI передаёт SDK буфер без проверки фактически возвращённого размера кадра. При несовпадении возможны отказ или некорректная работа с буфером; проявление на E3ISPM требует проверки.

**Уточнение для E3ISPM:** по приведённым при взаимной сверке данным августовской отладки размер 5440×3648 получен через `get_StillResolution` для выбранного индекса 0, и снимки сохранялись. Это свидетельство работоспособности данного индекса в проверенной конфигурации, а не доказательство совпадения всех списков. Приоритет для целевой модели можно снизить, но замечание не закрывать; новые испытания в рамках этого ревью не выполнялись.

**Устранение:** выбирать still из списка still, проверять каждый HRESULT и размеры, проверять фактическую информацию кадра и ёмкость буфера, явно обрабатывать отсутствие поддержки Snap.

### R18 — P1. Ответ USB-разрешения теряет extras при FLAG_IMMUTABLE

**Место:** `ToupcamController.requestUsbPermission()` (выбор `FLAG_IMMUTABLE` на API ≥ 31 и чтение `EXTRA_PERMISSION_GRANTED` с default=false).

**Подтверждение по проверенному пути AOSP:** SystemUI кладёт результат в дополнительный Intent и вызывает `PendingIntent.send(context, 0, intent)`. `PendingIntentRecord.sendInner()` выполняет `finalIntent.fillIn()` только при отсутствии `FLAG_IMMUTABLE`. Для текущего обработчика extras не доставляются, поэтому даже согласие пользователя интерпретируется как отказ. Когда USB-доступ уже получен через автооткрытие приложения, ветка запроса пропускается — это объясняет возможную работоспособность стенда.

Это блокирующий сбой подключения с видимым сообщением об отказе, а не тихая подмена данных. Прежнее возражение, основанное на официальном примере с `FLAG_IMMUTABLE`, снято после проверки исходников платформы. Сам пример противоречит этому пути доставки; особенности целевой прошивки проверить отдельно.

**Устранение:** `FLAG_MUTABLE` на API ≥ 31, сохранить ограничение получателя через `setPackage`; при ответе дополнительно проверять `usb.hasPermission()` для исходно запрошенного устройства. `setPackage` ограничивает пакет, но не задаёт конкретный ComponentName — эти понятия не смешивать. Сопоставлять ответ с запросом, корректно обрабатывать отказ и отключение устройства.

**Проверка:** запуск с уже подключённой камерой без ранее выданного доступа → согласие/отказ в диалоге; логировать наличие extras и итог `hasPermission`. Отдельно проверить автоматическое открытие при подключении и повторное подключение.

Источники: [UsbDialogHelper — отправка ответа](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/packages/SystemUI/src/com/android/systemui/usb/UsbDialogHelper.java), [PendingIntentRecord — условие immutable](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/core/java/com/android/server/am/PendingIntentRecord.java), [UsbUserPermissionManager](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/usb/java/com/android/server/usb/UsbUserPermissionManager.java). Проверена опубликованная ветка master; это не испытание всех версий Android/OEM.

### R19 — P2. Несколько контроллеров владеют одной нативной камерой

**Место:** `CameraModule`, `CamLib.java` (`sInstance`, статический `localHandler`), `jnicam.cpp` (`gHcam`), `AndroidManifest.xml`.

DI выдаёт отдельные контроллеры VM, но Java/JNI держат один общий handle и получатель событий. При перекрытии времени жизни контроллеров новый open может закрыть чужой handle, а release старого — закрыть новую сессию. Обработка `USB_DEVICE_ATTACHED` без явной стратегии повторного запуска Activity добавляет риск нескольких владельцев; утверждение «каждое переподключение обязательно создаёт Activity» без проверки маршрута запуска слишком сильное.

**Устранение:** единый владелец сессии, явные acquire/release и сериализация операций. Один `@Singleton` не решает проблему, если любая VM по-прежнему может безусловно освободить общий ресурс. Согласовать launchMode/onNewIntent с навигацией и проверить повторное открытие. При переиспользовании контроллера учесть инвалидацию FFC-кэша (R11).

### R20 — P2. Правила резервирования и защита учётных данных не определены

**Место:** `AndroidManifest.xml` (`allowBackup=true`), `backup_rules.xml`, `data_extraction_rules.xml`, `ServerSettingsStore`.

Пароль хранится в обычном DataStore, явные исключения резервирования не заданы. Настройки, БД и файлы могут попасть в системное резервирование; фактическая передача зависит от настроек устройства, транспорта и ограничений backup. Утверждать, что весь архив уже ушёл в облако, нельзя.

**Устранение:** отдельно определить защиту секретов и резервирование архива; исключить секреты из backup, выбрать хранение с ключом Android Keystore. Не отключать резервирование всего архива автоматически под выдуманное требование «данные не должны переезжать без сервера». Если резервирование поддерживается, проверить согласованность БД, JPEG, FFC и восстановление путей. `EncryptedSharedPreferences` не принимать как безусловную рекомендацию для новой реализации: API помечен deprecated ([Android Developers](https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences)).

### R21 — P2. Пиковое потребление памяти требует измерения

Кадр 5440×3648 в ARGB_8888 занимает около 79.4 МБ (75.7 МиБ); нативный RGB24-буфер добавляет около 59.5 МБ (56.8 МиБ). Дополнительно нужны превью, FFC, кодирование JPEG и UI. OOM на целевом устройстве пока не воспроизведён.

**Устранение:** измерить Java/native/общий пик на серии снимков и при FFC, проверить срок жизни буферов. Рассмотреть кодирование прямо из RGB24 без лишней ARGB-копии. `largeHeap` — только возможный измеренный запас, не первая мера и не гарантия устойчивости. Освобождение буферов согласовать с потоком событий SDK.

### R22 — P2. Эталон FFC принимается без проверки качества

Пересвеченный эталон теряет информацию о неравномерности, слишком тёмный усиливает шум. Существующий путь сохраняет уменьшенный размытый шаблон без критерия пригодности.

**Устранение:** проверять насыщение, минимальный полезный сигнал и статистику по каналам до принятия эталона; пороги определить на мишени для каждого освещения. При отказе сохранить прежний подтверждённый эталон. Встроенный `Toupcam_FfcOnce` оценить как альтернативу, но не считать автоматически эквивалентным текущему алгоритму и требованиям переноса профилей.

### R23 — P2. Переключение профиля теряет несохранённые настройки

**Место:** `CameraProfilesViewModel.selectLamp()`, `CameraProfilesScreen`.

При переключении лампы рабочая копия заменяется сохранённой версией другого профиля; уход с экрана также не предлагает сохранить черновик. Предупреждение перед перезаписью профиля не решает потерю несохранённых изменений.

**Устранение:** при отличии working от saved предложить сохранить/отбросить/отменить переход либо хранить отдельные черновики. Во время AE/AWB/FFC переходы согласовать с R13. Проверить оба направления переключения, Back и импорт.

Цепочка вызовов существует, но полностью «исправной» её назвать нельзя: есть гонки, преобразование и ограничения gain. Нужны HRESULT, readback, модель и режим SDK. |
| 5. AWB | Фиксированные 600 мс, отсутствие проверки и колбэка подтверждены | Ожидание результата и сохранение нативных значений обоснованы. Утверждение о неточности обратной формулы как причине неработающего AWB слишком сильное: `2^(v/64)` и `round(64*log2(x))` взаимно обратны в используемой модели; отдельно теряется G, если SDK вернул ненулевой зелёный gain. |
| 6. Индикатор | Подтверждено: маленькие метки в HUD, LampSwitch не получает состояние снятых слоёв | Предложение подходит. Показывать «снят» после успешной фиксации слоя, не после нажатия Snap. |
| 7. Блокировка съёмки | Ключевая гонка подтверждена | Дополнить R08–R10 и R13. Mutex только для capture/AE/AWB/FFC не исключит параллельный `applyProfile/switchLamp/release`. Системное закрытие процесса блокировка Back не предотвращает. |
| 8. Ориентация | Portrait и отсутствие адаптивной компоновки подтверждены | `configChanges` — выбор стратегии, а не гарантия сохранности TextureView/USB. Даже при живой Activity Compose может пересоздать AndroidView при смене ветки layout. Нужна повторная привязка Surface к тому же контроллеру, сохранение состояния, проверки multi-window и process recreation. |
| 9. Вынос керна | Несовпадение U+0441 и ASCII `c` подтверждено в локальном снимке конфигурации | Это подтверждает несовместимость ключей с этим снимком, но не даёт права назвать причину на текущем живом S900 окончательно доказанной. Исправить источник снимка; серверный контракт и миграцию данных согласовать. Подробнее ниже. |
| 10. Подписи глубин | Подтверждено | Предложенные подписи и адаптивная компоновка подходят. Добавить валидацию, автосохранение и доставку изменений на сервер: косметическое переименование не исправляет R01/R15. |

Для предложенной компоновки превью поведение размеров сверено с [реализацией AspectRatio в AndroidX](https://github.com/androidx/androidx/blob/androidx-main/compose/foundation/foundation-layout/src/commonMain/kotlin/androidx/compose/foundation/layout/AspectRatio.kt). Сам `blit` при совпадении размеров bitmap и Surface не искажает изображение: основной подтверждённый источник растяжения — TextureView; fit-center внутри blit является защитой для иных размеров Surface.

### Возможности SDK, которые следует проверить до собственного алгоритма

В локальном `toupcam.h` присутствуют:

- `TOUPCAM_OPTION_AUTOEXP_POLICY`: Exposure Only / Exposure Preferred / Gain Only / Gain Preferred — задать согласованную политику явно.
- `put_AutoExpoEnable(2)` (once), события `AUTOEXPO_CONV`/`CONVFAIL`, статус сходимости — вместо фиксированного ожидания 1.8 с.
- `TOUPCAM_OPTION_AUTOEXPOSURE_PERCENT`: замер по яркой доле изображения; оценить для контроля пересвета, но не обещать нулевой клиппинг без проверки полного снимка после FFC.
- `get_RealExpoTime`, диапазоны выдержки/gain, чтение WB/gamma — аудит фактически принятых настроек.
- `LINEAR` и `CURVE` (в заголовке дефолты 1 и 2), WBGAIN, BYTEORDER и другие параметры ISP — фиксировать поддерживаемые значения и читать результат, проверять HRESULT. Не отключать всю обработку без оценки качества; сохранять версию SDK и модель камеры.
- `Toupcam_FfcOnce`, FFC export/import — сравнить качество, поддержку моделью, влияние на preview/still и переносимость эталона с текущей программной FFC.

Наличие API в заголовке не гарантирует поддержку конкретной прошивкой. Результат readback после кадра при параллельном изменении профиля не доказывает параметры именно этого кадра: применять вместе с сериализацией R10/R13.

### Уточнения к AE (FIXES §2)

1. Пороги `0.01%`, `235–250`, гамма `2.2`, число итераций и пропускаемых кадров — проектные предложения, а не подтверждённые параметры камеры. `gamma=100` в SDK само по себе не доказывает конкретную степенную кривую выходного RGB. Выбирать параметры нужно по измерениям/контракту SDK.
2. Проверка по редкой сетке пикселей не гарантирует отсутствие маленьких пересвеченных областей. Для конечного контроля заявленного порога нужен полный кадр либо явно оговорённая статистическая погрешность и ROI. Поканальные доли и доля пикселей «хотя бы один канал пересвечен» — разные критерии.
3. У насыщенного пикселя неизвестна исходная яркость. Один контрольный snap с последующим уменьшением выдержки без повторной проверки не подтверждает итог. Нужен проверенный результат, ограниченное число попыток и честный исход «не удалось подобрать».
4. Критерий «максимум канала 235–250» противоречит разрешению небольшого числа пикселей 255. Следует отдельно определить перцентиль, абсолютный максимум, долю клиппинга и исключение дефектных пикселей.
5. Уточнить этап измерения: после FFC до JPEG или уже в декодированном JPEG. Проверять обещание про сохранённый JPEG нужно на JPEG.
6. В дополнительных требованиях AE сформулирована неоднозначно: §2.1 говорит «минимизировать выдержку», §3.1 предпочитает экспозицию усилению. Предложение FIXES увеличивать выдержку до максимума — разумная интерпретация приоритета малого gain, но требуется явно утвердить диапазон допустимой выдержки и критерий качества.

### Уточнения к WB (FIXES §4–5)

Диапазон 0.25..4 для каждого независимого R/G/B не помещается автоматически в текущую схему относительных gains. При G=0.25 и R=4 отношение равно 16, затем `toWbGain` ограничивает результат до 127. Появляются большие участки ползунка без изменения картинки. Диапазоны должны соответствовать принятому представлению, лучше хранить нативные параметры без неоднозначного пересчёта.

Предложение убрать G или перейти на Temp/Tint меняет дополнительные требования о трёх независимых каналах. Нужен согласованный выбор. Оценка программного WB «гарантированно работает, около 100 мс» не подтверждена измерениями: умножение уже обработанного 8-битного RGB не восстанавливает насыщенные данные и не доказывает корректную цветопередачу. Фиксировать порядок WB/gamma/FFC и измерять время на целевом телефоне.

Ограничение AWB для UF следует оставить согласуемым решением, как и обозначено В3, а не безусловным новым требованием. Белая/серая мишень и метод калибровки должны соответствовать используемому освещению.

### Уточнения к серверной схеме (FIXES §9)

Проверка `json.loads(attributes_ru.json)` завершилась ошибкой **Extra data: line 101 column 3 (char 2888)**. Первый JSON-объект корректен, но после него лежит ещё **820 символов** дублированного оборванного текста. Для анализа прочитан только первый объект; сам файл не исправлялся. Рекомендованный FIXES тест по ресурсу пока нельзя вводить с этим файлом без восстановления валидного источника. В `app/src/test/resources` такого эталона сейчас нет.

В первом объекте действительно:

- `сore_recovery` начинается с U+0441; остальные ID ASCII;
- `perforation_number`, все показанные глубины/поправка и сам `сore_recovery` имеют `type=String`;
- отсутствует `wellbore`, присутствуют `note` и `inclinometry`.

В таблице FIXES упущено расхождение типа самого `core_recovery`: клиент DOUBLE, снимок сервера String. Автоматически менять все типы по файлу нельзя: он конфликтует с инженерным контрактом и не подтверждает поведение backend при приёме чисел. Нужны актуальная схема и интеграционная проверка.

Миграция старого ключа должна быть согласована и для чтения, и для редактирования, и для экспорта. Изменений только `toJsonObject/decodeToStrings` недостаточно, если `encode()` затем перебирает другую схему и отбрасывает ключ. ASCII-тест допустим для внутренних канонических ID, но не для сырых серверных ключей при временной поддержке кириллического alias. Динамическая загрузка схемы не мигрирует автоматически уже сохранённые значения.

## 4. Что нужно согласовать в документах и с S900

1. **Статус MVP.** Бизнес-ТЗ требует реальные загружаемые поля; инженерное допускает встроенную схему. Интерфейс сейчас показывает дату «загрузки», хотя сети нет. Временно обозначать источник как встроенную конфигурацию; полноценную серверную схему считать отдельным незавершённым требованием.
2. **Основная камера.** Обновить инженерное ТЗ с Camera2 на фактический Touptek SDK и прописать поддерживаемые модели, диапазоны и подтверждение ручных параметров. Не объявлять Camera2 работающим резервом без отдельной проверки UI, разрешений и ориентации.
3. **Повторная отправка.** Определить замену, удаление, номер стола, пустые/неполные пары и идентичность назначения. Нужна явно описанная семантика, а не только POST первого экспорта.
4. **Завершение обработки.** Сейчас `postupload_processing=true` передаётся до загрузки всех изображений. По исходникам Android нельзя определить, начнёт ли S900 обработку неполного проекта. Согласовать момент финализации и подтверждение построения Core; это открытый вопрос, не доказанный серверный дефект. SENT сейчас означает окончание клиентского цикла запросов, а не готовность фотокниги.
5. **Глубины, масштаб и тип изображения.** Подтвердить контракт `kernUpperDepth/kernLowerDepth`, очистку значений, допустимость `UNKNOWN`, необходимость `pixelSize` и критерий правильной раскладки в каротаже.
6. **Повторяемость изображения.** Вместо непроверяемого обещания побитового совпадения кадров задать измеримые допуски цвета/яркости/геометрии, стабильные настройки и условия освещения, идентичность камеры и версии калибровки. Сам факт одинакового JSON не доказывает одинаковый физический результат.

7. **Поиск принятого файла на S900.** Возвращается ли исходное имя JPEG, в каком поле, когда оно становится видимым и как различать незавершённый запрос и отсутствие изображения? Проверить восстановление по конкретной версии файла (R06).
8. **Backup, формат и релиз.** Согласовать резервирование архива отдельно от секретов. JPEG максимального качества прямо предусмотрен инженерным ТЗ: переход на PNG/TIFF — изменение требований после измерений, не обязательное исправление самого факта JPEG. Отключённый R8 и versionCode=1 сами по себе не блокируют первый выпуск; отдельно проверить процедуру подписи и обновления.

9. **Лимиты загрузки.** Проверить максимальный размер файла и multipart-запроса, ограничения приложения S900 и прокси, таймауты, доступность чанковой загрузки и поведение при превышении. Использовать реальные JPEG максимального разрешения с камеры и несколько сцен. Размер «10–15 МБ», лимит «1 МБ по умолчанию Spring» и предположение о маленьких кадрах предыдущего сквозного теста не являются установленными фактами для этого развёртывания. Проверку проводить параллельно клиентским исправлениям; она блокирует приёмку передачи реальных кадров, а не работу над R01/R02/R05.
10. **Слияние схем атрибутов.** Выяснить, `attributes.json` дополняет или заменяет дефолтные `CORE_*`, существует ли уже латинский `core_recovery`, какие типы и значения есть под обоими ключами, как разрешаются совпадения ID. До ответа не выполнять простое серверное переименование кириллического ключа: возможны конфликт или необходимость миграции. Конкретное поведение backend пока не подтверждено.
11. **Синхронизация документации разработчика.** После согласования контрактов обновить `TOUPCAM_SETUP.md` (лимит превью: в коде 1280, фактическое разрешение может выбираться fallback), `ANDROID_KERN_APP.md` (основной Touptek-путь, сессионная авторизация вместо Basic, актуальные паспортные типы) и `CLAUDE.md`. Типы не менять автоматически по повреждённому локальному снимку. Результаты прежних испытаний отделить от подтверждений текущей версии.

## 5. Рекомендуемый порядок работ и приёмка

1. **Первая группа:** R01 (метаданные после POST), R09 (ошибка pull не должна становиться успешным кадром), R08 (безопасная замена файла), R18 (USB-разрешение). Диагностику USB провести на целевом телефоне; затем проверить исправление.
2. **До обновления рабочего архива:** R07 — миграции обязательны до установки версии с изменённой схемой поверх пользовательских данных. R11 — исключить перезапись подтверждённого FFC без сохранения.
3. **Надёжная отправка:** R02–R06 и R12; согласовать замену/удаление, назначение и восстановление принятого POST. До этого не считать SENT достаточным основанием для очистки архива.
4. **Камера и профили:** R10, R13, R14, R16, R17, R19, R21–R23; диагностировать WB/AE и возможности SDK. Исправления UI FIXES §1/3/6/10 можно выполнять рядом, но они не закрывают риски данных.
5. **Паспорт и эксплуатация:** FIXES §9, R15, R20, автосохранение, ориентация и итоговая проверка изображения/нагрузки.

Не откладывать целые группы 3–5 до всех ответов: ожидание относится только к зависимым задачам. Возможность написать исправление без оборудования не означает возможность принять его без испытаний. Проверку лимитов S900 и диагностику камеры вести параллельно первой группе.

**Временная эксплуатационная мера:** до исправления ложного SENT (в том числе R01/R02/R03/R05) ограничить действие «Очистить отправленные» либо требовать независимого подтверждения полноты серверного архива. Это предложение для реализации/регламента; в рамках этого ревью UI не изменялся.

### Минимальные решения MVP и дальнейшее развитие

| Область | Достаточный первый шаг | Когда нужна более сложная схема |
|---|---|---|
| Метаданные | ID сразу после POST + отдельное подтверждение PUT, сбрасываемое при правке | Ревизии при разрешённых одновременных правках |
| Отправка | Блокировка правок/удаления долбления и изменения назначения на время задачи; защита от повторного enqueue | Версионирование и условная фиксация ответов для работы без блокировки |
| FFC | Уникальные неизменяемые файлы при пересъёмке и импорте, переключение ссылки только после подтверждения; полная предварительная проверка импорта | Хеши и история калибровок для аудита; восстановление многошагового импорта после сбоя |
| Замена на сервере | Сохранить прежний remote ID и реализовать подтверждённый контракт замены; незавершённые удаления не терять | Полный журнал операций при сложной двусторонней синхронизации |
| Потеря ответа POST | Проверить поиск по имени версии JPEG и явно обрабатывать неопределённость | Серверная идемпотентность для гарантии отсутствия дублей |

Блокировки должны действовать в слое данных/операций, не только на кнопках. Более простой MVP не должен выдавать неподтверждённый результат за успешный.

Минимальный набор будущих проверок:

| Область | Обязательные сценарии |
|---|---|
| Repository / Room | Пересъёмка с аварией на границах file/DB commit; миграции старых БД; глубина до досъёмки; ведущие нули паспорта |
| Сеть с управляемыми ответами | Сбой PUT после POST; потеря ответа POST; повтор после изменения глубин; 404 проекта; 401/403; смена назначения/пользователя; правки в ходе отправки |
| Реальный S900 | Один FoV на стол, правильные DAYLIGHT/UF и `stackUid`; замена без дублей; паспорт включая вынос керна; построение Core и глубины в фотокниге |
| Телефон + Touptek | Холодный USB-запрос с согласием/отказом и проверкой extras/hasPermission; повторное подключение и несколько владельцев; спуск сразу после смены профиля; отключение USB при Snap; ошибочный pull; длинные выдержки; readback параметров; FFC без сохранения/после импорта; выход в фон и возврат |
| Изображения | Круг/квадрат без искажения; нейтральная мишень; пересвет до/после FFC/JPEG; повторяемость после перезапуска; различия preview/still |
| Нагрузка / адаптивность | 50+ столов, свободное место на исходе, серия полнокадровых снимков с измерением Java/native-памяти, планшет/ландшафт, поворот во время съёмки, восстановление после уничтожения процесса |

## 6. История уточнений

- Принято подтверждение USB-дефекта по AOSP; прежняя оценка «только гипотеза» снята. Видимый отказ отделён от тихой порчи/подмены данных.
- Снята избыточная оговорка к aspectRatio для конкретного предложенного Box.
- Устаревший FFC-кэш после импорта перенесён из текущих дефектов в риски переиспользования контроллера. Неявная перезапись эталона остаётся подтверждённой.
- R17 ограничен реально известным успешным индексом целевой камеры, без обобщения на все разрешения/модели.
- R06 дополнен проверяемой идеей поиска по имени версии файла, без ложного обещания идемпотентности.
- Зафиксировано согласие по минимальному R01: ID после POST, отдельное подтверждение PUT. Рекомендация переносить ID за PUT отклонена.
- Добавлены замечания по владению камерой, backup, памяти, качеству FFC, черновикам профилей и возможностям SDK. Приоритеты и варианты MVP пересмотрены.
- После дополнительной сверки добавлены лимиты реальных загрузок, слияние серверной схемы, единый реестр Q01–Q15, зависимости групп и список P3. Уникальные эталоны явно обязательны также при импорте. Возможность начать реализацию отделена от условий приёмки.

Текущие шаблонные тесты не подтверждают перечисленные свойства. Этот отчёт задаёт проверяемые дефекты и направления исправления; он не заменяет сборку и приёмку на целевом оборудовании.
