## 1. Превью растянуто на весь экран

**Симптом.** Картинка с камеры на экране съёмки искажена: кадр 3:2 растягивается на экран
телефона ~9:20.

**Причина.**
- `CaptureScreen.kt:79`: `AndroidView(TextureView)` занимает `Modifier.fillMaxSize()`.
- `CaptureViewModel.kt:107`: буферу `SurfaceTexture` задан размер кадра превью
  (`setDefaultBufferSize(previewSize)`), а `TextureView` по умолчанию растягивает буфер на весь
  свой размер, пропорции не сохраняет.
- `ToupcamController.kt:357` (`blit`): `drawBitmap(bmp, null, Rect(0, 0, canvas.width, canvas.height))`
  рисует кадр на весь холст.
- То же в редакторе профилей: `CameraProfilesScreen.kt:~180`, `CameraProfilesViewModel.kt:109`.

**Решение.**
1. Сделать общий компонент `ui/components/CameraPreview.kt` (одна реализация для обоих экранов):
   `Box(fillMaxSize, contentAlignment = Center)`, внутри `AndroidView(TextureView)` с
   `Modifier.aspectRatio(previewW / previewH)`. Размер берётся из `CameraControllerState.Ready.previewSize`.
   Получаются поля по краям, как в `TableViewScreen`.
2. В `blit()` на всякий случай рисовать с сохранением пропорций (прямоугольник fit-center, фон
   `Ink`), чтобы Surface любой формы не искажал кадр.
3. **Сверка пропорций превью и снимка.** Сейчас превью выбирается как «самое большое разрешение с
   шириной ≤ 1280» (`jnicam.cpp`, `openDevice`), а снимок — как максимальное (5440×3648 = 1.491).
   Если соотношения сторон разные, кадрирование в превью не совпадёт со снимком. В `openDevice`
   выбирать превью с тем же соотношением сторон, что у снимка (допуск ~1 %); отдавать в Kotlin
   оба размера (уже есть `getPreviewSize`/`getStillSize`) и логировать оба.
4. Горизонтальный вариант (п.8) использует этот же компонент.

**Файлы.** `CaptureScreen.kt`, `CameraProfilesScreen.kt`, новый `ui/components/CameraPreview.kt`,
`ToupcamController.blit`, `jnicam.cpp` (`openDevice`).

**Проверка.** Снять круг или квадратную мишень: на превью и в сохранённом JPEG форма одинаковая,
без овала. Повернуть устройство (после п.8): кадр по-прежнему не искажён.

## 2. Автоэкспозиция без пересвета: гистограмма на весь диапазон

**Симптом.** После автоэкспозиции в кадре есть пересвеченные области (видно и на скриншоте `img_1.png`).

**Причина.** `ToupcamController.autoExposure` (`:131–149`) включает **штатную непрерывную AE** SDK
(`setAutoExpoEnable(1)`), ждёт фиксированные 1.8 с и замораживает то, что получилось. Штатная AE
Touptek держит **среднюю** яркость около цели `AutoExpoTarget` (по умолчанию 120 из 255). Светлый
керн на тёмном лотке → среднее низкое → AE добавляет выдержку → светлые участки уходят в 255.
Пересвет AE никак не контролирует. Кроме того:
- 1.8 с при 8 fps — примерно 14 кадров; сошлась ли AE, не проверяется (`TOUPCAM_OPTION_AUTOEXPO_CONV`
  не читается);
- FFC (§2.3) после съёмки **умножает** края кадра (`mean / tmpl > 1`), поэтому даже без пересвета в
  превью края снимка могут упереться в 255 при `clamp`.

**Требование (сформулировано).** Экспозиция подбирается так, чтобы:
- (а) пересвеченных пикселей не было, с допуском на битые/горячие пиксели, например не более 0.01 %
  пикселей с каким-либо каналом ≥ 254;
- (б) верх гистограммы стоял как можно ближе к правому краю, в целевом диапазоне 235–250 по самому
  яркому каналу (принцип «expose to the right»);
- (в) усиление не росло без необходимости: сначала подбирается выдержка, gain поднимается только
  при упоре в максимальную выдержку.

**Решение — собственная AE по гистограмме (итерационная).**
1. **Натив (`jnicam.cpp`)**: функция `computeStats()` по последнему кадру превью (буфер RGB24 уже
   есть в `pullInto`). Возвращает поканальные гистограммы 256 бинов (или сразу нужные перцентили):
   `hiR/hiG/hiB` (например, 99.99-й перцентиль), долю пикселей ≥ 254 по каждому каналу и `lo`
   (0.1-й перцентиль). Считать по прореженной сетке (каждый 4-й пиксель), этого хватает.
   Альтернатива — `Toupcam_GetHistogramV2`, но свой расчёт прозрачнее и заодно учитывает FFC.
2. **Kotlin (`ToupcamController.autoExposure`)**:
   - выключить авто-AE SDK, gain = 100 % (1.0x);
   - цикл до ~8 итераций: выставить выдержку → **пропустить 2–3 кадра** (новая выдержка
     применяется с задержкой) → взять статистику → скорректировать;
   - коррекция: если есть клиппинг — сжимать выдержку делением пополам (значения в 255 ничего не
     говорят о реальной яркости); если клиппинга нет — `t *= (target / hi)^γ`, где γ ≈ 2.2 при
     гамме профиля 100 % (выход ISP нелинейный; точнее — обратить кривую `gamma` профиля);
   - стоп: `hi ∈ [235, 250]` и клиппинг ≤ порога;
   - упор в `AE_MAX_TIME_US` при недосвете → поднимать gain тем же циклом;
   - в конце ОДИН контрольный снимок (`snap`) с проверкой той же статистикой, потому что превью
     может отличаться от полного кадра (биннинг/ISP). Если в снимке есть клиппинг, уменьшить
     выдержку на рассчитанную величину.
3. **Учесть FFC**: если у профиля есть эталон, статистику считать по кадру **после** коррекции
   (натив умеет `flatFieldCorrect`; для превью применять по уменьшенному шаблону) или оставить
   запас, равный максимальному усилению шаблона `max(mean/tmpl)`.
4. **Нижний край («недосвет»).** Выдержка масштабирует всю гистограмму, поэтому растянуть её влево
   одной выдержкой нельзя. Если нужно «на весь диапазон» в полном смысле, это растяжка уровней
   (black point). Предлагается отдельный **необязательный** параметр профиля «Уровень чёрного»
   (`Toupcam_put_LevelRange` low, high = 255): рассчитывается той же процедурой как `lo`, но
   **фиксируется в профиле** и не меняется от кадра к кадру, чтобы дневной и УФ-снимки разных
   столов оставались сопоставимы. По умолчанию выключен. → Открытый вопрос В1.
5. **UI.** Индикатор прогресса уже есть (`AutoProc.EXPOSURE`); добавить итог в тосте: «Выдержка X,
   усиление Y, пересвет 0 %». В редакторе профиля — маленькая гистограмма превью (из той же
   `computeStats`) с отметкой пересвета, чтобы оператор видел результат и при ручной настройке.

**Файлы.** `jnicam.cpp`, `CamLib.java` (новые `native`), `ToupcamController.autoExposure`,
`CameraProfile` (+ `blackLevel`, если принято), `ToupcamProfileApplier`,
`CameraProfilesScreen`/`ViewModel` (гистограмма).

**Проверка.** Сцена «белая бумага + тёмный лоток»: после АЭ в сохранённом JPEG доля пикселей 255
≤ 0.01 %, максимум канала 235–250. Повторный запуск АЭ на той же сцене даёт ту же выдержку (±1 шаг).

## 3. Убрать параметр «Фокус»

**Причина.** `CameraProfile.focusDistance` пришёл из модели Camera2 (`LENS_FOCUS_DISTANCE`,
диоптрии). Для Touptek он **игнорируется** (`ToupcamProfileApplier`, комментарий в шапке): фокус у
камеры механический. При этом он показывается:
- ползунок «Фокус … дптр» — `CameraProfilesScreen.kt:94–99`;
- строка HUD «… · Фокус ∞» — `CaptureScreen.kt:192–193`;
- неиспользуемая строка `camera_profiles_focus` в `strings.xml:118`.

**Решение.**
- Добавить в `KernCamera` признак возможностей, например `val capabilities: CameraCapabilities`
  с `supportsFocus` (Touptek = false, Camera2 = true, если `LENS_INFO_MINIMUM_FOCUS_DISTANCE > 0`).
  Ползунок и часть HUD показывать только при `supportsFocus`. Фактически для основной камеры они
  исчезнут.
- **Поле в модели оставить**: оно нужно запасному пути Camera2 (`CameraProfileApplier:51–54`), а
  удаление сломает десериализацию сохранённых профилей в DataStore и экспорт/импорт (§4.2).
- Удалить неиспользуемый строковый ресурс.

Проще, но хуже: убрать ползунок безусловно. Тогда запасной путь Camera2 останется с фокусом из
дефолта (∞).

**Файлы.** `KernCamera.kt`, `ToupcamController.kt`, `CameraController.kt`, `CameraProfilesScreen.kt`,
`CaptureScreen.kt`, `strings.xml`.

## 4. Ползунки R/G/B не влияют на картинку

**Что проверено в коде — цепочка на стороне приложения исправна:**
ползунок → `vm.update()` → `_working` → `collectLatest { controller.applyProfile() }`
(`CameraProfilesViewModel.kt:84–88`) → `ToupcamProfileApplier.apply` → `CamLib.setWhiteBalanceGain`
→ `Toupcam_put_WhiteBalanceGain` (`jnicam.cpp:270`). Выдержка и gain идут тем же путём и работают,
значит обрыв ниже, в SDK или камере.

**Вероятная причина (гипотеза, проверить на камере).**
1. У Toupcam **два взаимоисключающих режима баланса белого**: *Temp/Tint*
   (`put_TempTint`/`AwbOnce`) и *RGB Gain* (`put_WhiteBalanceGain`/`AwbInit`), см. `toupcam.h:681–693`.
   Если камера (E3ISPM — модель с аппаратным ISP, `TOUPCAM_FLAG_ISP`) работает в Temp/Tint, вызовы
   RGB Gain возвращают ошибку (`E_NOTIMPL`/`E_UNEXPECTED`) и ничего не меняют.
2. **Коды возврата SDK нигде не проверяются**: все сеттеры в `jnicam.cpp` — `void`, `HRESULT`
   отбрасывается. Поэтому сбой не виден.

**Сопутствующие недочёты (исправить в любом случае).**
- Диапазон ползунков `1f..4f` (`CameraProfilesScreen.kt:100–117`): коэффициент нельзя опустить
  ниже 1.0, то есть нельзя «убрать красный». Нужен диапазон 0.25..4 (лог-шкала).
- Ползунок **G** меняет только отношение (в SDK уходит `R/G`, `0`, `B/G`): если двигать G, картинка
  меняется «наоборот» (R и B ослабевают). Предложение: либо убрать G (зелёный — опорный, так принято
  в RGB-Gain модели Touptek), либо подписать его «Зелёный (опорный)» и честно пересчитывать. → В2.

**Решение.**
1. **Диагностика (первый шаг, 1 билд).** В `jnicam.cpp` все сеттеры возвращают `HRESULT` и пишут его
   в лог `JNI_CAM`. Дополнительно логировать `Toupcam_get_Model` → `flag` (есть ли `FLAG_ISP`),
   `get_WhiteBalanceGain` сразу после `put`, `get_TempTint`. На камере подвигать ползунок и
   посмотреть лог.
2. **Если RGB Gain не поддерживается** — переходим на Temp/Tint:
   - в applier переводить R/B профиля в температуру/оттенок через SDK-функцию
     `Toupcam_Gain2TempTint` (есть в `toupcam.h:1657`) и вызывать `Toupcam_put_TempTint`;
   - либо (чище) хранить в профиле `wbTemp`/`wbTint` и показывать ползунки «Цветовая температура, K»
     (2000–15000) и «Оттенок» (200–2500). Это меняет UI, поэтому решение за заказчиком (В2).
3. **Если RGB Gain поддерживается, но эффекта нет** — проверить `TOUPCAM_OPTION_WBGAIN`
   (встроенное WB-усиление, по умолчанию 1) и `TOUPCAM_OPTION_ISP`; выставлять явно в `openDevice`.
4. **Запасной вариант (гарантированно работает).** Программный баланс белого в нативе: в `pullInto`
   умножать каналы на коэффициенты профиля (для превью и снимка одинаково), аппаратный WB держать
   нейтральным. Детерминированно и не зависит от прошивки. Минус — чуть больше CPU на 20-Мп кадре
   (порядка 100 мс на снимок, приемлемо).
5. Ошибки SDK поднимать в Kotlin (`Result`/исключение) и показывать тостом, а не глотать.

**Файлы.** `jnicam.cpp`, `CamLib.java`, `ToupcamProfileApplier.kt`, `CameraProfilesScreen.kt`,
`CameraProfile.kt` (если Temp/Tint).

**Проверка.** Ползунок R на максимум → кадр заметно краснеет в превью **и** в сохранённом JPEG;
значение переживает перезапуск приложения и переключение Дневной/УФ.

## 5. Автобаланс белого не работает

**Причина.** `ToupcamController.autoWhiteBalance` (`:154–171`):
- вызывает `Toupcam_AwbInit` (режим RGB Gain) без колбэка и **без проверки результата**. Если камера
  в Temp/Tint (см. п.4), вызов ничего не делает;
- ждёт фиксированные 600 мс (≈ 5 кадров при 8 fps; one-push AWB может не успеть), затем читает
  `get_WhiteBalanceGain`. При неуспехе там `[0,0,0]` → множители 1.0/1.0;
- сразу вызывает `ToupcamProfileApplier.apply(updated)`, то есть **перезаписывает** то, что сделал
  AWB, пересчитанными значениями. Из-за неточной обратной формулы `2^(v/64)` возможен сдвиг.

Итог совпадает с наблюдением: «что-то делает (прогресс крутится), на картинку не влияет».

**Решение.**
1. Та же диагностика, что в п.4, — определить режим WB.
2. Вызывать API нужного режима **с колбэком**: `Toupcam_AwbOnce(h, tempTintCb, ctx)` для Temp/Tint
   или `Toupcam_AwbInit(h, wbCb, ctx)` для RGB Gain. Колбэк передаёт итоговые значения в Kotlin
   (через `OnEvent`/отдельный метод), `autoWhiteBalance` ждёт его через `suspendCancellableCoroutine`
   с таймаутом ~5 с (по образцу `snapStillBlocking`).
3. Сохранять в профиль **ровно то**, что вернул колбэк, в той же единице, что применяет applier
   (без обратных пересчётов), чтобы повторное применение давало идентичную картинку.
4. Если аппаратный AWB не заработает — **программный AWB** (дополняет п.4.4): по кадру превью
   считаются средние R/G/B по светлым ненасыщенным пикселям (white-patch/gray-world, исключая
   ≥ 250) → `gainR = G/R`, `gainB = G/B` → в профиль.
5. **Для УФ-профиля** AWB по смыслу неприменим: флуоресценция не нейтрально-серая, и «баланс белого»
   исказит свечение. Кнопку АББ в режиме УФ блокировать или показывать предупреждение. → В3.
6. Инструкция перед запуском (как для FFC): «положите в кадр белый/серый лист».

**Проверка.** Белый лист под тёплым светом → после АББ лист в превью и JPEG нейтральный
(R≈G≈B ±3 %); значения R/B в редакторе изменились; повторный АББ даёт те же значения.

## 6. Отметка «кадр снят» — перенести на переключатель освещения

**Сейчас.** Маленький текст «Дневной ✓ / УФ ✓» в правом верхнем углу HUD
(`CaptureScreen.kt:125–127`, `CaptureIndicator`). Сегменты `LampSwitch` о съёмке ничего не знают.

**Решение.**
- `LampSwitch(selected, onSelect, captured: Set<LampType>, enabled: Boolean)`. У снятого сегмента:
  - иконка «check_circle» (Material Symbols) перед подписью;
  - **рамка 2dp** цвета `Green30` (токен уже есть в `Color.kt`) и подпись «Дневной · снят».
  - Цвет заливки активного сегмента не трогаем (синий/тёмный с жёлтым), иначе пропадёт различие
    «выбран / снят». Рамка и галочка работают независимо от выбора.
- Не снятый кадр — без изменений; когда сняты оба — оба сегмента с галочкой (стол готов).
- Старый индикатор в HUD убрать, номер стола оставить.
- Для доступности: `contentDescription` «Дневной, кадр снят».
- `LampSwitch` используется и в редакторе профилей — там `captured` пустой (параметр по умолчанию).

**Файлы.** `ui/components/LampSwitch.kt`, `CaptureScreen.kt`, `strings.xml`, при необходимости
токен `KernTokens.borderStrong = 2.dp`.

## 7. Прогресс съёмки и блокировка UI

**Симптом.** Пока снимается кадр, можно переключить освещение и снова нажать «Снять» — один кадр
теряется.

**Причина (точная).**
1. Блокируется только кнопка спуска (`CaptureScreen.kt:156`, `enabled = !capturing`). Переключатель
   освещения, «Новый стол», «Готово» и системный «Назад» активны.
2. **Тип освещения читается после снимка**: `CaptureViewModel.kt:152–153`
   ```kotlin
   val profile = controller.capture(file, _lamp.value)          // снимок 20 Мп длится секунды
   repository.saveLayer(layerId, tableId, _lamp.value, file, profile) // _lamp уже другой!
   ```
   Если за время снимка переключиться на УФ, **дневной кадр сохранится как УФ**. Следующее нажатие
   «Снять» на УФ перезапишет этот слой (`saveLayer` заменяет слой той же лампы и удаляет файл,
   `KernRepository.kt:147–151`). Дневной кадр пропадает.
3. `switchLamp` во время снимка применяет УФ-профиль **посреди экспозиции** — кадр получается с
   чужими параметрами.
4. `newTable()` во время снимка обнуляет `_tableId` — кадр может уйти в новый стол.
5. `ToupcamController` держит одного ожидающего `pendingStill`: второй `snap` затирает первый, и
   первая корутина висит до таймаута 15 с.

**Решение.**
- В `capture()` **зафиксировать** `lamp`, `tableId`, `profile` в локальные `val` до начала съёмки и
  использовать только их.
- `switchLamp`, `newTable` — ранний выход при `_capturing.value == true`.
- В `ToupcamController.capture`/`captureFfcReference`/`autoExposure`/`autoWhiteBalance` — общий
  `Mutex`: второй снимок параллельно невозможен даже при ошибке UI.
- UI во время съёмки:
  - полупрозрачная подложка поверх экрана (перехватывает касания) + `CircularProgressIndicator`
    вокруг кнопки спуска + подпись «Снимок… не двигайте лоток»;
  - `LampSwitch(enabled = false)`, кнопки «Готово»/«Новый стол» disabled;
  - `BackHandler(enabled = capturing) {}` — блокирует системный «Назад».
- Прогресс: у SDK нет процента для снимка → **неопределённый** индикатор. Этапы для подписи: «Съёмка»
  (snap → EVENT_STILLIMAGE) → «Обработка» (FFC) → «Сохранение» (JPEG + миниатюра). Можно отдавать
  `StateFlow<CaptureStage>` из VM.
- Тайм-аут и ошибка (камера отключилась) → снятие блокировки + тост, стол не создаётся, если кадр не
  сохранён (сейчас стол создаётся до снимка, `CaptureViewModel.kt:145–150`; перенести создание
  после успешного `capture`).

**Файлы.** `CaptureViewModel.kt`, `CaptureScreen.kt`, `LampSwitch.kt`, `ToupcamController.kt`.

**Проверка.** Нажать «Снять» и сразу пытаться переключить УФ, нажать «Новый стол», «Назад» — ничего
не происходит до конца снимка; в галерее дневной кадр на месте и помечен как дневной.

## 8. Горизонтальная ориентация (телефон/планшет)

**Сейчас.** `AndroidManifest.xml:31` — `android:screenOrientation="portrait"`; все экраны свёрстаны
колонкой.

**Решение.**
1. **Манифест**: убрать `screenOrientation` (или `fullUser`) и добавить
   `android:configChanges="orientation|screenSize|screenLayout|smallestScreenSize|keyboardHidden"`.
   Тогда Activity не пересоздаётся: USB-сессия камеры, `TextureView` и снимок в процессе не рвутся
   при повороте. Compose сам перекомпонует вёрстку.
2. **Определение макета**: `currentWindowAdaptiveInfo()` / `WindowSizeClass` (material3-adaptive).
   Правило: ширина ≥ Medium **или** ландшафт → «двухпанельный» вариант.
3. **Экраны:**
   - **Съёмка** (главное): превью слева (компонент из п.1, fit-center по высоте), справа
     вертикальная панель ~ 30 % ширины: номер стола → `LampSwitch` (вертикальный вариант, п.6) →
     кнопка спуска → «Новый стол»/«Готово». В ландшафте кадр 3:2 занимает экран почти целиком — это
     и есть основной выигрыш.
   - **Редактор профилей**: превью слева, прокручиваемые ползунки и авто-кнопки справа.
   - **Стол (`TableViewScreen`)**: изображение слева, слои и поля глубины справа.
   - **Списки, форма, настройки, очередь**: одна колонка с ограничением ширины `widthIn(max = 640.dp)`
     по центру, чтобы на планшете поля не растягивались.
4. **Камера не вращается вместе с телефоном.** Внешняя Touptek закреплена на штативе, её кадр в
   системе координат лотка не зависит от поворота телефона, поэтому превью **не поворачиваем** (в
   отличие от Camera2). Для запасного Camera2-пути поворот учитывается через `SENSOR_ORIENTATION`.
   Нужно для него проверить.
5. `windowSoftInputMode="adjustResize"` сохранить: в ландшафте клавиатура занимает полэкрана, формы
   должны прокручиваться (`imePadding`).
6. Токены §14 — без новых цветов; при необходимости добавить `KernTokens.sidePanelWidth`.

**Файлы.** `AndroidManifest.xml`, `build.gradle.kts` (`material3-adaptive`), все `ui/screens/*`,
`LampSwitch.kt` (вертикальный вариант), `CameraPreview.kt`.

**Проверка.** Телефон и планшет (или эмулятор Pixel Tablet), поворот на каждом экране; поворот во
время снимка не теряет кадр и не переподключает камеру.

## 9. «Вынос керна» не приходит в S900

**Причина (точная).** В конфигурации атрибутов S900 (`attributes_ru.json`) идентификатор поля
записан с **кириллической буквой «с»** (U+0441) вместо латинской «c»:

```
"id": "сore_recovery"      ← байты: d1 81 6f 72 65 5f ... («с» кириллица + "ore_recovery")
```

Клиент (`Passport.kt:34`) шлёт латинский ключ `core_recovery`. Для сервера это **другой**
атрибут: значение уходит в тело `POST/PUT /analysis/source` (плоский ключ, `@JsonAnySetter`), но к
полю «Вынос керна, м.» не привязывается и в карточке проекта не видно. Остальные ключи совпадают
побайтно (проверено: других не-ASCII символов в `id` нет), поэтому они и пришли.

**Решение.**
1. **Правильно — исправить опечатку на сервере**: переименовать атрибут в `core_recovery` (латиница)
   в конфигурации полей S900. Это чинит и клиент, и любые другие интеграции, и поиск/фильтры.
   Выяснить, есть ли на сервере уже заполненные значения под кириллическим id, и нужна ли их
   миграция. → В4 (к владельцам `s8`).
2. **Если сервер править нельзя** — временно слать ключ побайтно как на сервере
   (`"сore_recovery"`, обязательно через `\u`-escape с комментарием, иначе опечатку «исправят»
   обратно). При переходе на динамическую загрузку полей (§10.1) проблема уходит сама: ключи
   берутся с сервера.
3. **Миграция локальных данных** (при варианте 2): у уже сохранённых долблений в `passportJson` лежит
   `core_recovery`. В `PassportCodec.toJsonObject`/`decodeToStrings` добавить таблицу
   переименований старый ключ → новый. Повторно отправить затронутые проекты: у отправленных
   сработает `PUT /analysis/source/{id}` (`DrillingUploader.kt:57`), нужно лишь пометить их dirty.
4. **Заодно сверить схему клиента с сервером** — найдены расхождения:

   | Ключ | Клиент (`PassportSchema`) | Сервер (`attributes_ru.json`) | Действие |
   |------|---------------------------|-------------------------------|----------|
   | `field` | «Месторождение/площадь» | «Месторождение» | выровнять подпись |
   | `wellbore` | есть («Ствол») | **нет** | убрать с клиента или добавить на сервер (В4) |
   | `perforation_number` | INTEGER | String | слать строкой (номер может быть «12а») |
   | `core_recovery` | латиница | **кириллическая «с»** | см. выше |
   | `depth_correction`, `initial_sampling_reference_*` | DOUBLE | String | слать строкой или согласовать тип; сейчас сервер получает JSON-число |
   | `note` («Примечание», многострочное) | **нет** | есть | добавить на клиент (текст, многострочное поле) |
   | `inclinometry` (File) | нет | есть | вне скоупа: загрузка файла, отдельная задача |

5. **Защита от повторения**: юнит-тест, что все ключи `PassportSchema` — ASCII
   (`key.all { it.code < 128 }`), и тест-сверка со снимком `attributes_ru.json` (лежит в
   `app/src/test/resources`).

**Файлы.** `domain/model/Passport.kt`, `data/PassportCodec.kt`, тесты; конфигурация S900 (вне репо).

**Проверка.** Заполнить «Вынос керна» → отправить → в S900 у проекта значение в поле
«Вынос керна, м.». Отредактировать и отправить повторно → значение обновилось (PUT).

## 10. Переименовать «Кровля» / «Подошва»

**Где.** Экран стола (`TableViewScreen.kt:271–285`), строки `strings.xml:52–54`.

**Решение.**
- `table_view_depth_upper`: «Кровля» → **«Верхняя граница керна, м»**
- `table_view_depth_lower`: «Подошва» → **«Нижняя граница керна, м»**
- Подсказку `table_view_depth_hint` «Глубина керна по столу (§8.5), м:» заменить на
  «Глубина керна по столу:». Ссылка на пункт ТЗ оператору не нужна, единица теперь в подписях.
- **Вёрстка**: длинные подписи в двух полях рядом (`Row` + `weight`) на телефоне обрежутся. Поля
  расположить **друг под другом** на всю ширину (портрет), кнопку «OK» — под ними или как
  trailing-иконку. В ландшафте (п.8) можно оставить рядом.
- `keyboardOptions = KeyboardType.Decimal` (если ещё не стоит).
- Паспортные поля «Исходная привязка отбора, кровля/подошва, м.» (`Passport.kt:38–43`) —
  **серверные** подписи, их не трогаем (иначе разойдутся с S900).

**Файлы.** `strings.xml`, `TableViewScreen.kt`.
